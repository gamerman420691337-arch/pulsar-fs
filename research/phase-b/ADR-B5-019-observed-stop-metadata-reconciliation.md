# ADR B5-019: Retry observed stop metadata without replaying a device effect

Status: implemented; current evidence and limits in ../../docs/PULSAR_STOP_COMPLETION_RECONCILIATION.md. Actual device/dispatcher and broader acceptance remain open.

Evidence: the durable stop handoff correctly retires host authority before attempting to write a matching callback outcome. If that write fails, the legacy Result reports JournalUnavailable, but the sealed stop is already retired. Repeating the callback would be refused, and the owner has no sealed recovery object retaining the already observed outcome for metadata-only retry.

Decision: add complete_stop_with_recovery returning an engine-constructed StopCompletionRecord. Validate current stop and exact receipt before retirement, retire host stop authority, capture the original effect/receipt/outcome, and attempt the same journal completion. Ok indicates that the callback matched and retired authority; callers must inspect journal_pending. Pending is an explicit incomplete metadata write, not acknowledged durable success. The record can explicitly persist only its captured outcome to its original receipt, under existing boot-ownership, immutable correspondence, stored-integrity and terminal-outcome consistency checks. It exposes no request or authority and cannot issue a physical effect. No automatic retry occurs.

A successful metadata retry after a newer stop or reconnect is historical recording only. It cannot retire that newer token, rearm playback, restore a controller/admission, or clear physical uncertainty. A newer engine boot fences the original record. Records are neither cloneable nor deserializable; process restart cannot invent an observed callback from an unknown prepared row. If the process loses a pending record, the stored outcome stays unknown and ordinary disarmed/stop-unconfirmed recovery remains required.

Compatibility: PreparedStopEffect, the journal schema/encoding/capacity, protocol and physical capabilities remain unchanged. Existing complete_stop_durable delegates to the new path and preserves its original Ok/JournalUnavailable behavior; callers that require recovery explicitly select the additive API and retain the returned object. No Sync/Send behavior changes to existing token types. Pending status is conservatively reset before each attempted persist so a failed retry cannot be represented as a current successful attempt.

Rejected alternatives: replaying the retired stop could duplicate an effect; updating outcome from arbitrary history facts would invent observation; restoring pending metadata as fresh authority violates restart fencing; treating callback acknowledgment or its later durable recording as physical proof violates the stopping contract. A new journal/portable schema is unnecessary because the original record already binds these facts.

Validation obligations: actual private SQLite UPDATE-abort injection, explicit same-receipt retry for both acknowledged/unknown outcomes, duplicate persistence, newer-stop noninterference, cross-boot refusal, reconnect uncertainty and receipt substitution. Tests use synthetic qualification facts and no actual transport. Complete runtime verification and host storage behavior, process death/power loss, full historical reconciliation/retention, actual Handy/firmware/clock/stop behavior, platforms, models/media, rendered GUI, human and release acceptance remain distinct open gates.
