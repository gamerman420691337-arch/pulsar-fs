# ADR B3-105: persistent runtime custody for AppImage clients

Status: implemented; current source-bound checks are recorded in the checkpoint. Scope: Linux x86-64 candidate first-use/cache verification and actual AppImage assembly.

Problem: the Engine deliberately outlives its originating client, but an AppImage runtime unmounts or removes temporary extracted contents after its entrypoint exits. Launching the Engine directly from transient application contents would make later worker/tool/runtime discovery depend on an expired path.

Decision: runtime-launch SOURCE CACHE_ROOT -- ARGUMENTS installs the bounded original candidate manifest into a new private manifest-SHA directory and launches the verified cached application. The existing installer preserves declared bytes, stage custody and no-overwrite publication. Different manifests coexist; no update/delete/rollback policy is implied. Create missing cache components through no-follow descriptors and explicit private modes, including restrictive umask. Require trusted non-writable ancestors except root-owned sticky directories; preserve and refuse unsafe roots. Serialize preparation with a private single-link nonblocking lock. An active preparation refuses with a retry diagnostic.

Before each launch, validate the exact original manifest, private integrity-bound local receipt, complete finite inventory, current ownership/device/link/mode admission, all payload lengths/SHA-256 and stable metadata. Check held directory/path bindings. Refuse a damaged/unknown cache and preserve it for inspection. Never repair, replace or delete a pre-existing entry. Unpublished installer stages remain eligible only for the existing explicit stage recovery commands. A killed creator before complete cache/lock creation can leave an untrusted entry that is preserved and refused; automatic cleanup remains open.

The AppImage's AppRun uses an explicit PULSAR_RUNTIME_CACHE_ROOT, otherwise absolute XDG_CACHE_HOME/pulsar/runtime or HOME/.cache/pulsar/runtime. It delegates verification/installation to the trusted executable and executes the persistent copy before Engine configuration. Host help/version/completion parsing also moves before per-user state/worker discovery. Cached execution removes transient AppImage location variables and preserves other owner environment choices. No model selection or host inference approval is fabricated.

The Linux builder consumes a candidate and exact pinned official appimagetool/type2-runtime assets, copies finite verified declared payloads into AppDir, retains original manifest bytes and supplies AppRun/desktop/SVG metadata. It invokes the tool with an explicit runtime file; no builder network fetch is required. File synchronization and atomic no-overwrite hard-link publication preserve an existing image. Temporary builder trees are removed on normal completion/refusal; process death and exhaustive publication/filesystem faults remain open.

API release snapshots and upstream license text are retained. This pins downloaded bytes; it does not establish independently verified signatures or transitive redistribution qualification.

The actual artifact remains an unqualified runtime candidate. Useful Core/Complete generation assets/defaults, installed advertised tiers, clean-machine/FUSE/OS/CPU/vendor/signing/license matrix, large/removable-filesystem behavior, upgrades/rollback, full native/live/media/device and human/release acceptance remain required.

Observed upstream limitation: this pinned runtime returns success in extract-and-run mode while retaining its extracted payload. Both original and diagnostic checks fail the automatic-cleanup assertion; normal FUSE launch passes on the recorded current host. The custody fixture explicitly removes its own extracted payload after parent exit and verifies later Engine/client/worker use from persistent assets. This is an interruption/teardown campaign, not proof of automatic upstream cleanup. Cleanup remediation and the independent full platform/release gate remain open.
