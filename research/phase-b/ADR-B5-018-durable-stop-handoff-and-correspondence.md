# ADR B5-018: Durable stop handoff and exact callback correspondence

Status: implemented; local software verification recorded in ../../docs/PULSAR_DURABLE_STOP_HANDOFF.md. Public physical playback, transport dispatch and device qualification remain open.

Evidence: starts already have a durable handoff API. Stops from explicit requests, controller loss, revocation and unknown play completion previously required the owner to assemble separate journal preparation/completion calls. A journal receipt is sealed but the owner could accidentally pair a valid receipt with another callback in the same boot. Existing journal metadata contains sufficient immutable facts to check correspondence without a schema change.

Decision: introduce an engine-constructed PreparedStopEffect pairing a stop token with its committed receipt. Explicit stop, controller loss and revocation have durable paths; a stop returned by unknown play completion can be passed through the same preparation path. Validate the stop kind and current token before preparation. Retain sealed single-use effect/session/admission/controller/configuration/qualification facts. Immediately before actual transport handoff, the owner must still recheck current authority and the prepared stop token, outside any blocking I/O.

A preparation failure returns no durable request, retires that stop token and leaves StopUnconfirmed with physical uncertainty. There is no automatic retry. An explicit fresh request or revocation can create another stop; capacity/ownership/integrity constraints remain mandatory. Full or unavailable journals do not become physical stopping evidence. An emergency physical stop mechanism and its behavior under journal failure remain device/dispatcher qualification obligations, not a guarantee supplied by this conditional API.

On a matching callback, validate the receipt's boot and content identity against the exact effect before changing runtime state. Then retire host stop authority and mark StopUnconfirmed before attempting journal completion. A completion write failure must not leave a callback current or imply that a new physical retry was authorized; persisted outcome remains unknown. Substituted or retired callbacks cannot settle another record. Completion borrows the sealed token, so an incorrect journal handle does not discard the caller's token before an explicit retry with its original journal. Neither acknowledgment nor successful journaling clears physical uncertainty.

Compatibility: existing low-level coordinator methods and durable start tuple remain available. Add stop-specific handoff and completion APIs plus a sealed token; the journal's version-1 record encoding, content ID, capacity and stored outcomes remain unchanged. Pure effect-record construction is shared by preparation and receipt validation. No client command, protocol, project/portable schema or transport capability changes. Actual owner/dispatcher integration must select these durable paths before enabling effects.

Rejected alternatives: journal calls manually assembled by every stop origin leave a correspondence gap; copying transport bodies/credentials to recovery storage is unnecessary; treating acknowledgment as physical evidence violates the core contract; automatic replay after restart could resume stale authority. A receipt mismatch is refused without changing the current stop.

Validation obligations: real private SQLite stores exercise prepared and completed stops, receipt substitution, fenced preparation/completion, quota refusal, revoked/lost/unknown-play routes, headless compatibility, pre-dispatch cancellation and reconnect/restart uncertainty. Tests use synthetic qualification facts and no device transport. Broader crash/power-loss, emergency-stop ordering, real Handy firmware/sync/stop, platform, human and release gates remain open.
