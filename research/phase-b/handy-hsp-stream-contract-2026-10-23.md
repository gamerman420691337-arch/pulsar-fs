# Handy HSP streaming implementation contract

Research date: 2026-10-23. This narrows the [October 22 timing/streaming research](handy-continuous-timing-and-streaming-2026-10-22.md) to an implementable REST codec and append protocol. Sources were fetched again from the manufacturer; no device endpoint, credential, build, or physical device was used. Findings describe public interfaces and manufacturer examples, not measured firmware behavior.

## Decision and evidence status

Implement a distinct HSP session with explicit setup, serialized append, play, state read, and stop. Its canonical position representation is **integer percent, 0–100**, and its absolute tail index is **zero-based cumulative points added minus one**. Both have direct manufacturer source support. The REST schema still says position `maximum: 50`; this conflict remains an explicit live compatibility limitation, not permission to halve coordinates. The sources provide no append idempotency, exclusive session lease, physical stop bound, or calibrated timing guarantee. [Point declaration][rpc-point], [manufacturer examples][examples-points], [append example][examples-add], [REST specification][spec]

The useful initial codec surface is below. These five endpoints all document a `DeviceResponse` envelope with `result: HspState`, unlike the bare-state schemas of pause/resume. “Consistent documented shape” does not mean observed live conformance. [REST specification][spec], [REST client][rest-hsp]

| Operation | Initial explicit request subset |
| --- | --- |
| `PUT /hsp/setup` | `{ "stream_id": <nonzero uint32> }` |
| `PUT /hsp/add` | `{ "points": [{"t": <integer milliseconds>, "x": <integer percent>}], "tail_point_stream_index": <absolute last index>, "flush": false }` |
| `PUT /hsp/play` | `{ "start_time": <integer script time>, "server_time": <estimated server milliseconds>, "playback_rate": 1, "loop": false, "pause_on_starving": false }` |
| `GET /hsp/state` | No body. |
| `PUT /hsp/stop` | No body. |

Omitting embedded Play/Add, flush, threshold changes, pause/resume and synctime is an initial implementation choice, not a claim that those operations are unsupported. Separate Add acknowledgment makes exact chunks easier to journal. No SDK sample was executed against a device.

## Setup, mode and identity

Setup clears the existing HSP session; its optional `stream_id` is generated by the server if omitted. A changed ID signals a new session, while skipping setup can modify an existing session. Supply a fresh nonzero ID in the documented `1..4294967295` range and compare every response to that ID. HSP is mode `4`; `/mode` separately returns `mode_session_id`. HSP state itself contains neither mode nor that mode-session identity. [REST specification][spec]

The SDK calls `/hsp/setup` directly and its examples proceed Setup → Add → Play without a separate mode write. This supports using Setup as the preparation operation; it does **not** establish an atomic, exclusive mode acquisition or make an old mode read current. Observe mode/session identity through the existing owner before admitting playback. Neither Add nor Play nor Stop carries an expected `stream_id` precondition, so an identity check cannot prevent another client replacing the stream between check and dispatch. A single local owner is necessary but cannot manufacture a device-side lease. [REST client][rest-hsp], [setup example][examples-setup]

The newer RPC comments also describe setup resetting clock/options, with FW4.4-specific filtering defaults. The RPC repository still labels itself a draft. Do not import those defaults into a deployed REST/firmware profile without verification. [RPC setup][rpc-setup], [RPC status][rpc-readme]

**Pre-Play option correlation:** the retrieved sources do not establish that Setup must return the complete tuple `playback_rate:1`, `loop:false`, `pause_on_starving:false`. REST's Setup example contains that tuple but also contains 100 buffered points and nonzero clock/tail values, so it is not a normative initialization snapshot. Its reported `playback_rate` schema has no default or minimum. The draft RPC Setup comment explicitly lists resetting `loop:false`, threshold/clock zero and filtering off, but does not list a rate or starvation-policy reset. The SDK supplies all three options in **Play**, whereas Setup sends only the ID. Therefore correlate Setup/prefill by identity, nonplaying state and expected buffer transition while retaining their well-formed observed options; enforce the requested option tuple on the acknowledged Play response and subsequent active observations. Requiring that tuple before Play would be an additional local restriction without a complete manufacturer Setup guarantee. This does not relax post-Play checks. [REST specification][spec], [RPC setup][rpc-setup], [REST client][rest-hsp], [Play serialization][rest-play]

## Points, indices and buffer ownership

**Position:** REST `PointPosition` describes 0–100 percent with 100 at the top and even gives 100 as its example, but declares maximum 50. The SDK's full-stroke arrays use `0 → 100 → 0`, and its REST Add function serializes `data` without coordinate conversion. The current owning RPC declaration explicitly corrects an older 0–255 comment: `x` is 0–100 percent; 100 maps to full stroke; larger values clamp. Therefore encode canonical percent unchanged, reject values outside 0–100, and never silently clamp or rescale to 50/255. Acceptance of REST positions 51–100 by the deployed server remains **UNKNOWN**; the public SDK and RPC intent do not prove its validator configuration. If strict schema compatibility is required, refuse those values explicitly rather than pretending 0–50 represents the full stroke. [REST specification][spec], [full-stroke examples][examples-points], [Add serialization][rest-add], [RPC correction][rpc-point]

**Tail:** the SDK command-pad converter sends `points.length - 1` initially and `pointsAdded + pointsToAdd.length - 1` for later chunks. Another demo increments the actual submitted count then sends `added - 1`. The RPC describes the field as the absolute index of the last added point. Maintain the cumulative count independently of the current buffer length: appending 20 points then 7 gives tails 19 then 26. Eviction does not reset this counter. [command-pad converter][converter], [chunked example][examples-add], [RPC Add][rpc-add]

REST requires a tail index of at least 1 and permits at most 100 points per Add. It specifies no minimum array length. Consequently a **local initial-subset rule** of at least two points avoids the zero-based single-point tail `0` conflict; later one-point appends are representable. Reject empty appends locally. This is not evidence that the firmware itself requires two points. `t` is an integer ≥0 in REST and uint32 in RPC; checked conversion to uint32 is source-supported. No universal interval, required timestamp separation, or dynamics limit was established. [REST specification][spec], [RPC Point][rpc-point]

Do not copy the convenience helpers as a normative algorithm. `HSP.fill` begins at zero when flushing and increments by the requested batch size even when the final slice is shorter. `hsp_utils` calculates a new tail from the previous reported tail and chunk length, which depends on the initial reported sentinel; its threshold expression reduces to the new tail for a nonnegative threshold. These helpers do not establish unambiguous initial-state or threshold behavior. No HSP/index/position tests were found in the public SDK's five `*.spec.js` files. [fill helper][fill], [stream helper][stream-push], [SDK tests][sdk-tests]

**Ordering and eviction:** SDK slices preserve caller order. The public REST text says a full buffer evicts the oldest points to accommodate new points; capacity comes from `max_points`. Playback does not imply the stored point count shrinks: the RPC comments say buffer extent/count changes when points are added or cleared. The retrieved contracts do not define duplicate timestamp, decreasing timestamp, late-point, duplicate Add or out-of-order-request handling. Use strictly increasing timestamps across acknowledged chunks as an explicit local policy, one in-flight append, and an independently tracked future horizon. Do not silently sort, backfill or resend late points. Capacity and tail arithmetic alone do not prove the points being evicted were already physically played. [REST specification][spec], [converter][converter], [state semantics][rpc-state]

**Ambiguous writes:** `tail_point_stream_index` is bookkeeping, not a documented deduplication key or compare-and-swap. A timeout after dispatch leaves the exact chunk's outcome unknown. Even an equal reported tail does not identify its point bytes or exclude another writer. Retain the request and outcome, stop admitting further motion, and require the existing reconciliation/new-session path; never blind-retry Add. This is the conservative application policy justified by the absence of a stronger promise in the request/response contracts. [REST specification][spec], [RPC Add][rpc-add]

## Play, starvation and stop

`start_time` is script time; the RPC permits negative values. `server_time` is the estimated server clock at sending, used for latency adjustment, not a separate future-execution deadline. REST says omission uses current server time, while the SDK explicitly defaults the field to zero. Supply an explicit estimate paired with the intended script time instead of adopting either omission/zero behavior. The manufacturer example pairs `HSP.play(0, ...)` with `sync.estimate()`. No source here supplies a bounded transfer function, future lead time, or dispatch jitter tolerance; those remain qualification inputs. [Play client][rest-play], [RPC Play][rpc-play], [play example][examples-setup], [REST specification][spec]

Set `loop:false`, rate `1` and the starvation flag explicitly. With `pause_on_starving:true`, documented stream time pauses while waiting for new points and resumes automatically when data arrives. That can diverge from media that kept playing. A media-following implementation can choose `false` and stop/refuse on starvation, but this is a policy choice; the response alone does not prove physical behavior at buffer end. Starvation and threshold SSE events are observations, not authority renewal or reliable delivery guarantees. [REST specification][spec], [RPC Play][rpc-play]

Use the actual bodyless Stop request. Flush is a separate buffer-clearing operation and has no documented stop guarantee. SDK `closeConsumer` only stops SSE/removes subscriptions; it sends no HSP Stop. Stop's response is another HSP state, with no published bound for physical rest and no promise that the buffer is cleared or retained. Preserve explicit unknown outcomes and measured stop requirements. [Stop client][rest-stop], [consumer close][stream-close], [REST specification][spec]

## Response decoding and limits

For the five selected operations, require a well-formed `result` and no `error`; HTTP 200 alone is insufficient because documented 200 responses include device-timeout/disconnected errors. Reject contradictory envelopes. SDK `ok` is manufactured from HTTP status, not a required wire property, and the request utility also accepts bare payloads. A strict REST codec should not inherit that permissive fallback silently. [REST specification][spec], [request utility][request]

The required HSP state fields are `play_state`, `points`, `max_points`, `current_point`, `current_time`, `loop`, `playback_rate`, `first_point_time`, `last_point_time`, `stream_id`, `tail_point_stream_index`, `tail_point_stream_index_threshold`, and `pause_on_starving`. Documented numeric play states are 0 uninitialized, 1 playing, 2 stopped, 3 paused, 4 starving. Preserve signed `current_point`, `current_time` and tail: RPC documents `current_point = -1` in a Play response and a special tail value of −1. Do not make every integer unsigned. REST calls `max_points` a number; RPC gives an integral uint32 capacity. Integral/finite validation and checked conversions can be explicit codec policy. [REST specification][spec], [RPC state fields][rpc-state-fields]

There is a known representation discrepancy: the SDK helper handles both numeric `4` and string `HSP_STATE_STARVING`, with an explicit API inconsistency TODO. The canonical subset should accept documented numeric states; unexpected strings require a visible unsupported-response result or a separately specified compatibility profile, not undocumented coercion. Public source does not establish which deployed responses use the string. [SDK state workaround][stream-state]

State is approximate and assembled across different instants. `current_point` can move backward and is not physical position; paused `current_time` can drift. Stream identity plus state is useful for diagnostics, not exact presentation evidence, effective-clock renewal, or proof that an appended trajectory was executed. Actual firmware, REST validation above 50, timestamp handling, buffer-overrun behavior, network loss, owner death and physical stopping remain unqualified. [owning state semantics][rpc-state]
