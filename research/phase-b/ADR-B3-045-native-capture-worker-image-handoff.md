# B3-045: Native capture worker retirement and image handoff

Status: Implemented; bounded local verification recorded in the terminal incremental checkpoint. Production GPU admission remains disabled.

The native byte-capture helper had its own child/cgroup reaper and combined CPU/storage reservation. A captured image outlives the copying worker. Shared worker retirement normally deletes snapshots, so using it unchanged would destroy the successful image; releasing the combined reservation would instead drop the image's storage accounting. The production engine currently refuses GPU launch before this helper. This decision supplies real capture custody and a committed-engine constructor, not completion of that missing GPU caller.

Use the existing `WorkerCustody` for the actual standalone capture caller, with custody installed before command construction and spawn. Add a consuming staging handoff: signal/poll the child, require every transport thread finished and the exact group empty, acknowledge group retirement/reclamation, then transfer the staging owner. Until all those observations succeed, keep ordinary custody installed so errors use its existing conservative cleanup/reaper behavior. No fallible operation follows removal of that owner.

Partition a reservation's storage charge without changing aggregate accounting. CPU/RAM/worker ownership stays with worker custody; storage stays with staging through a retained owner. This lets confirmed capture-worker retirement release CPU capacity while the image remains charged. Staging cleanup retains that charge until deletion and, for durable staging, journal clearing are acknowledged. Recursive retention uses an erased ownership boundary to avoid unbounded generic type expansion; this changes no wire format.

A private tracked capture constructor consumes the caller's held engine fence. Independently require the committed schema-20/minimum-4 binding, matching scope and exact canonical state directory before reservations or creation. Create durable staging and pass both prepared staging and the CPU claim through admitted cgroup creation. It never opens a second engine scope or upgrades an uncommitted helper declaration. This ownership constructor is not model/provider authorization or offline/GPU scheduling admission. The capture itself still runs in the confined native-copy role without loading supplied libraries or mounting GPU devices.

The successful image owner disarms its redundant nested-directory destructor; the encompassing staging owner performs deletion. Copy completion, independent metadata adoption, actual worker retirement and image disposal remain distinct observations. A path or a sent kill alone proves none of those transitions.

Required evidence includes independent storage/CPU release order, native capture success and wrong-byte failure using a committed actual engine lease, blocked image deletion with retained storage/lease, failed handoff with an unretired transport and preserved bytes/claims, preceding worker-retirement and creation regressions, native capture of the declared library set, cancellation/deadline cases and broader affected gates. See [the incremental packet](../../docs/evidence/roadmap-2026-10-07/native-capture-custody/gates.json).

This does not enable engine GPU jobs. Connect capture to fresh device/resource admission, mounted image/device integrity, worker execution/result acceptance, cancellation and restart before that gate changes. Legacy orphan recovery, reboot/root relocation, full crash/IO bounds and model/media/platform/Handy/human/release qualification remain separate work.
