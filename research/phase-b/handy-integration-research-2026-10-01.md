# Handy integration: protocol evidence and qualification boundary

Research date: 2026-10-01. User selected the Handy family; actual variant and firmware are unspecified. No hardware was contacted, credentials used, commands sent, packages installed, or paid services accessed.

## Pulsar contract

The active checkout's `docs/PULSAR_SOFTWARE_SPECIFICATION.md` §12 requires Handy including Handy 2, online and optional offline BLE, explicit online script/command consent, and no silent BLE-to-cloud fallback. SAFE-01–05 require disarmed reconnect, rejection of stale commands, profile-specific stopping, and physical qualification of thresholds. No numerical command-age, disconnect, or stop bound has been agreed.

`docs/PULSAR_ARCHITECTURE_DECISIONS.md` CONTRACT-09 requires exclusive ownership/controller, revision-pinned admission, exact driver/device/firmware/transport qualification, and human acceptance where applicable. `crates/pulsar-core/src/device.rs` already separates `StopRequested`, `StopUnconfirmed`, and engine-qualified stop evidence; `HeadlessApproval` needs a qualified stopping bound. A HTTP/BLE acknowledgment must not manufacture `DeviceObservedStopped` or a qualification record.

## Online control

- V3's production base is `https://www.handyfeeling.com/api/handy-rest/v3`; firmware before v4 is unsupported. Authentication uses `X-Api-Key` or bearer token plus device `X-Connection-Key`. HSSP v3 cannot load private-network script URLs. The schema has two actionable defects: `/hdsp/xpt` declares required `xa,va` despite defining `xp,t`; `PointPosition` describes 0–100 and examples 100 but declares maximum 50. Do not silently resolve either contradiction or use generated types as qualification. [V3 OpenAPI](https://www.handyfeeling.com/api/handy-rest/v3/docs/spec.yaml).
- Account login access tokens are not direct API credentials; application IDs/keys are issued separately. [Official API authentication guide](https://ohdoki.notion.site/Handy-Rest-API-v3-ea6c47749f854fbcabcc40c729ea6df4?pvs=21).
- V2 bases include `/api/handy/v2` and `/api/handy-rest/v2`. `PUT /hssp/setup` supplies a device-fetchable script URL, optionally SHA-256; documented CSV maximum is 524288 bytes. `PUT /hssp/play` uses camelCase `estimatedServerTime,startTime`; `PUT /hssp/stop` stops playback; `GET /hstp/sync` synchronizes device/server clocks. [V2 OpenAPI](https://www.handyfeeling.com/api/handy-rest/v2/docs/spec.yaml).
- V3 SDK uses `PUT /hssp/play` with `start_time,server_time,playback_rate,loop`; stop is a bodyless `PUT /hssp/stop`. HSP similarly provides `PUT /hsp/setup` with `stream_id`, `/hsp/add`, `/hsp/play`, `/hsp/stop`, and `/hsp/flush`. These are separate operations; a flush is not a documented physical stop. Models are enumerated separately (H01, H01_2, H02, H02_pro, H02_eco); a family label is insufficient to select a profile. [Pinned manufacturer client source](https://gitlab.com/sweettechas/platform/handyfeeling-utils/-/blob/190784911d0ef920a38decb52e1cf5594be6338e/handy-rest-api-v3-client/src/index.mjs#L1510-1924).
- HSP initializes a new session; add accepts at most 100 points and discards oldest points if full. State includes `stream_id`, capacity, and tail index. Default API device response timeout is 5000 ms (allowed 5000–60000); this is not a stopping bound or acceptable live delay. `pause_on_starving:true` pauses the device clock and resumes when more points arrive; unsuitable as an implicit faithful-media policy. [V3 OpenAPI](https://www.handyfeeling.com/api/handy-rest/v3/docs/spec.yaml).
- The SDK's HSP source sends bounded batches, tracks tail indices, prevents simultaneous pushes, and removes a consumer if its stream changes. These are useful software references, not proof of loss recovery. [Pinned HSP utility](https://gitlab.com/sweettechas/platform/handyfeeling-utils/-/blob/190784911d0ef920a38decb52e1cf5594be6338e/ohdoki-sdk/src/hsp_utils.mjs).

**Implementation recommendation:** use an explicitly selected API family and fixed production origin, bounded TLS requests, no redirects, in-memory credentials loaded through environment-name references, and redacted receipts. All status/time/auth service calls require online opt-in; consent must bind script hash/revision, transport, and allowed purpose. HSSP setup may expose generated motion via its hosting URL, so hosting is a separate disclosed effect; media/prompts/provenance stay local. Do not automatically fall back to v2, upload, alter firmware, or issue a new connection key.

## BLE: verified coverage and missing details

The [current official BLE guide](https://ohdoki.notion.site/Bluetooth-control-1ee344f4b55d42e5be14d98b001ee504) calls integrations self-supported and publishes FW4 service `77834d26-40f7-11ee-be56-0242ac120002`, TX `77835032-40f7-11ee-be56-0242ac120002`, RX `77835410-40f7-11ee-be56-0242ac120002`. Advertising is `ohd_hwX_*`. It says FW4 has separate RX/TX and fuller RPC support, but supplies no packet envelope, fragmentation, write properties, correlation schema, HSP message IDs, or stop procedure in the retrieved page. Those details remain **UNKNOWN**; UUIDs alone cannot implement a qualified transport.

The [official FW3 guide](https://ohdoki.notion.site/Bluetooth-control-FW3-11d33fbce0474330b80d3b47beef838c?pvs=21) discourages new applications on the old protocol and describes immediate unbuffered position/time commands. The vendor's [legacy README](https://gitlab.com/sweettechas/handy/handy-ble-client/-/blob/77c6479268f12808db59a56902a89d7f1b925375/README.md) specifies firmware `3.0.0-beta2+`, Linux BlueZ/D-Bus implementation, Protocomm Security0, Protobuf payloads on `handyplug`, information handshake and heartbeat. A returned `MaxPingTime` describes connection reset, **not physical stopping**. Do not claim Windows/macOS coverage or apply this envelope to Handy 2/FW4.

Legacy [handyplug.proto](https://gitlab.com/sweettechas/handy/handy-ble-client/-/blob/77c6479268f12808db59a56902a89d7f1b925375/handy/handyplug.proto) defines payload repeated messages, LinearCmd field 403, uint32 request ID/device index, vectors with uint32 index/duration and double position. It defines Ping/OK/Error/handshake but no explicit stop command. [Legacy client](https://gitlab.com/sweettechas/handy/handy-ble-client/-/blob/77c6479268f12808db59a56902a89d7f1b925375/handy/handy.py) correlates replies by IDs and sends periodic pings. Moving to zero/midpoint is not a substitute stop.

The [Handy 2 manufacturer guide](https://www.thehandy.com/handy-2-how-to-guide/) separately lists offline classic/pattern use, online setup, and Bluetooth remote setup. This establishes product features, not third-party arbitrary script protocol coverage or exact firmware compatibility.

**Implementation recommendation:** implement codec/mock fixtures only for the verified legacy family, marked deprecated/unqualified. FW4 discovery UUID constants and capability rejection can be implemented now; motion writes remain unavailable until an owning-source wire contract and offline stop behavior are verified. Do not infer encoding from unrelated or community snippets.

## Shared clock, stop, and command-age policy

Manufacturer [time-sync guidance](https://ohdoki.notion.site/Time-Syncing-49cda199db034c0493ec029b70194422?pvs=21) uses milliseconds and a common server clock; it labels its code API v2 and recommends v3 for new apps. The [functionality guide](https://ohdoki.notion.site/Handy-functionality-2a5b14198a6c4204b270c47521fb5da9?pvs=21) explains HSSP setup followed by play with media position and estimated server time, and explicitly acknowledges synchronization limitations from network distance, player time, video processing, and screen refresh. HDSP immediate movement does not establish synchronized playback.

Recommended scheduler contract: use a monotonic presentation clock plus a measured wall/server mapping and uncertainty; separate capture-to-command, command acknowledgment, player synchronization, and physical lag. Freeze motion revision/profile/epoch at admission. Reject backward timestamps, stale epochs, elapsed deadlines, changed firmware/configuration, unknown clock mapping, and infeasible adaptation. Stop clears host queues and cancels producers before transport stop; failed/ambiguous stop enters `StopUnconfirmed`. Reconnect, source/controller loss, process restart, or transport change never replay/rearm. Requested stop, acknowledged API stop, reported remote state, and qualified physical stopping remain distinct. Select command-age/jitter/disconnect numbers only from measured configuration evidence; no universal 200 ms limit can be invented here. Headless playback remains unavailable without human-approved device-side failure stopping evidence.

## Offline test fixtures and remaining acceptance

Derived **codec-only** legacy KAT: ID=1, device/vector index=0, duration=1000 ms, position=0.5 encodes as `0a139a191008011a0c10e80719000000000000e03f`. Proto3 zero fields are omitted. Compare against an independent Protobuf implementation before adopting; bytes do not constitute actuation qualification. Bound decoder lengths, validate finite position in [0,1], positive duration, IDs, response type, and malformed/truncated frames. [Owning schema](https://gitlab.com/sweettechas/handy/handy-ble-client/-/blob/77c6479268f12808db59a56902a89d7f1b925375/handy/handyplug.proto).

Mock online sequence: absent consent produces zero requests; explicitly selected v3 setup uses fresh stream ID; successful setup permits fixture additions then explicitly approved play; stop acknowledgment remains stop-requested/unconfirmed without qualification. Test 401/429/timeout, nonempty API error with HTTP200, state mismatch, changed stream/device session, overflow, blocked slider, stale server mapping, late add after stop, redacted URLs/headers, absent controller, and recovery after an ambiguous dispatch. V2 and v3 payload KATs must reject cross-family camelCase/snake_case substitution. Keep HSP position-bound and HDSP required-field contradictions as explicit unresolved compatibility tests.

Physical qualification still requires identified serial/model/firmware/OS/BLE adapter or online configuration, exact driver/profile artifacts, travel/dynamics measurements, stop/disconnect/engine-death behavior, external-player synchronization, and human stopping acceptance. Source inspection, mocked acknowledgments, successful transmission, and a status response cannot close those gates. This research does not qualify any hardware.
