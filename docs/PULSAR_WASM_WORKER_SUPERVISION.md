# Linux WASM worker supervision

Status: verified local Linux supervision with an authenticated editor integration. GB-12 remains incomplete.

This increment adds the engine-side `wasm_launch` helper. It takes the shared ResourcePool and an already owned durable WorkerFence; it cannot grant permissions or commit project state. The [authenticated editor workflow](PULSAR_AUTHENTICATED_WASM_EDITING.md) now invokes it with per-invocation native/module identity approval, authorization and revision fences. The configured native worker executable remains trusted engine configuration. Each Linux invocation now opens a regular, non-symlink executable, captures at most 128 MiB into a fully sealed anonymous file, and supplies its held descriptor to Bubblewrap `--perms 0500 --ro-bind-data`. Bubblewrap copies the sealed bytes into a private read-only file mount; there is no mutable-path fallback. That child-side copy is covered by the existing whole-worker memory budget. During namespace setup only, the native file-size limit is the larger of the captured executable length and output budget; the real WASM worker lowers both soft and hard file limits to the declared output budget before compilation or guest execution. Private output/tmp mount limits remain enforced throughout. The supervisor reports the exact captured executable hash and byte length. Expected-build authorization now binds startup and captured executable identity; captured runtime dependencies remain a release obligation.

The worker wire now requires `WasmWorkerRequest { version, attempt_id, request }` and returns `WasmWorkerResponse { version, attempt_id, output }`. A bare processing declaration is refused. The data ABI remains `pulsar.buffer.v1`; neither a manifest nor an attempt ID creates authority. The parent rechecks the captured module hash before creating work, then verifies response version/attempt, ABI, module/input/output hashes, output byte budget and fuel ceiling. Data remains an untrusted proposal requiring later semantic/project admission.

## Supervision and ownership

The helper reserves the child memory declaration, a 16 MiB bounded parent transport margin and the complete executable image length from the supplied shared pool before capture. The sealed image follows WorkerCustody, including unresolved retirement/reaper ownership; a mutable original path cannot change the launched image after capture. It uses existing format-4 cgroup creation, durable fence registration, WorkerCustody, nonblocking pipes and process-tree retirement. The child runs with Bubblewrap isolation, a read-only runtime/executable, private proc/dev/tmp/output mounts, cleared environment, cgroup physical-memory/CPU/pid limits and existing process rlimits. No project, source, device or user-secret directory is mounted. The guest has no imports or broker calls.

Input JSON remains bounded to 4 MiB. Response JSON is separately bounded to four times the 64 KiB data limit plus 4096 bytes for metadata, covering the worst-case numeric-byte JSON representation. The same parent deadline/cancellation monitor covers blocked stdin, stdout, stderr and direct-child waiting. Diagnostic retention is bounded to 16 KiB and reads are budgeted per tick. Native Wasmtime compilation is inside that process boundary. Guest memory reservation is explicitly 16 MiB with no growth reservation and a 64 KiB guard; guest Store memory bounds remain separate from native process limits.

Success requires valid egress, successful exit, confirmed whole-tree retirement and a final deadline/cancellation check. Errors get a bounded retirement observation; unresolved custody and its admission reservation transfer to the existing reaper. Direct-child exit does not by itself release authority/resources. Format-4 fence/creation records and inode identity protect cleanup; no parent or unrelated cgroup is modified by the launcher.

The deadline starts before validation/admission. Existing fence/cgroup creation and host filesystem helpers retain their own obligations; a blocked host filesystem operation is not proven preemptible by the worker timer. Cross-platform containment, aggregate fairness/live scheduling, exhaustive compiler/OOM/CPU-limit stress and independent host-storage deadlines remain qualification work.
