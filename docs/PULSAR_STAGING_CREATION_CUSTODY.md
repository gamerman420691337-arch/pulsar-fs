# Creation-error staging custody

Status: admitted creation prototype implemented under the existing Linux test-only staging lifecycle module. Production fence format 3 and engine integration remain pending. This increment does not repair the production owner-death counterexample.

The retained [counterexample source](evidence/roadmap-2026-10-07/staging-creation-custody/before.rs) and [failing log](evidence/roadmap-2026-10-07/staging-creation-custody/before.log) demonstrate a lost identity acknowledgement after directory creation: authored bytes remain, but the caller's reservation drops and reserved storage becomes zero rather than 4,096 bytes.

The admitted prototype installs a custody guard before fallible host operations. It retains the reservation, attempted journal record and held parent/root descriptors together. It captures the root before parent sync and identity publication. If creation returns an error, no byte-user handle has escaped: checked retirement/cleanup runs through the shared cleanup retry owner. Existing resources without captured identity remain ambiguous; their names alone do not authorize deletion. A successful creation requires explicit independent byte-user retirement before cleanup; dropping its exposed handle conservatively retains custody, because Rust handle lifetime does not prove that an OS worker has retired. Production worker/capture transfer must supply that proof.

Retirement publication precedes deletion. Confirmed deletion precedes an exact-obligation, idempotent durable clear. Publication, deletion or clear errors retain admission. A confirmed retirement publication is not republished on clear retries. The custom cleanup task drops captured claims before publishing completion; the existing spawn/panic custody guard also retains the task state. Spawn/panic failure injection has not been independently qualified by this increment.
