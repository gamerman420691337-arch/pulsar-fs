# WASM catalog recovery and unsuccessful-attempt removal

Status: targeted local implementation and lifecycle checks pass. This increment does not close plugin or release qualification.

`wasm-edit list PROJECT` returns up to 64 retained status reports for the authenticated session and project. Original start request IDs allow a client to recover the attempt ID after a lost acknowledgement. Reports contain bounded status/receipt facts, never captured module/input/output buffers. Other sessions have separate catalogs even when they hold project Read grants. A request absent from this catalog does not prove it was never executed.

`wasm-edit remove-unsuccessful PROJECT ATTEMPT --original-request-id ID --expected-state failed|cancelled|interrupted` requires current Read+Edit authority, the original owning session, exact project/attempt/start request and the observed terminal state. An active worker registry entry refuses removal even after a terminal status was written. On Linux, a conservative engine-wide worker-fence check also refuses while a creation, live-group or deferred-retirement obligation remains. This may delay cleanup while unrelated work runs; it does not kill that work. Running attempts and completed candidate evidence cannot be removed. Removal and its request replay receipt commit atomically; repeated identical removal returns the original receipt. Changed requests refuse. Existing start-request identity/response records remain, so replaying a removed attempt's original start request cannot execute the guest again. Removal does not commit, retime, truncate or otherwise change master motion.

Clients validate response kind, project, attempt, original request and state correspondence. Catalog responses reject duplicates, foreign-project reports, more than 64 operations and encoded status data exceeding the control-frame admission. Nothing is truncated. The CLI requires the observed original request and unsuccessful state before constructing removal intent. No cleanup is automatic, and no user project is pruned as part of these tests. The database schema and portable format are unchanged.

Completed records still retain the original invocation bytes required by portable candidate history and count against the global 64-operation admission limit. Separating durable candidate evidence from operation discovery, user-facing retention quotas, broader recovery and GUI approval/status remain required. Native/runtime/processor roles, host deadline/resource/formal qualification, model/media/annotations, platform, Handy and human/release gates remain open.

The explicitly run delegated Linux fixture confirms an actual guest trap, exact original-request recovery through listing, foreign-session isolation, Read-only removal refusal, refusal while an injected operation registry entry remains, stale intent refusal, removal replay, preserved master bytes and a new completed proposal after capacity is restored. Capacity uses 63 synthetic terminal rows plus one real failed worker; it does not establish 64 real executions. Completed invocation evidence still captures into a portable archive. Restart preserves the removal, completed/synthetic records and original start-request replay, without launching another worker.
