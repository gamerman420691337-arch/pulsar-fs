# Strict Rust CUDA worker sessions

`worker::cuda_session::CheckedCudaSession` implements an actual Rust CUDA adapter under the Linux `cuda` feature. Production profile admission remains CPU-only; this adapter is currently exercised through the authored namespace probe, not the job/attempt path.

The wrapper holds the [SDK device](PULSAR_CUDA_SDK_IDENTITY.md) through session creation, all calls and profiling. Identity is checked before and after creation, each successful inference and final profiling. The native session drops before the held driver. Only copied float32 output shapes/values leave the wrapper; no native session or output value can escape its driver lifetime. The caller must supply broker-captured model/runtime/driver identities, confinement, reservations, private trace storage and process supervision.

Creation rejects an already initialized ONNX environment and enables CUDA registration errors and disabled CPU fallback. It pins the requested logical ordinal, arena limit, SameAsRequested growth and disabled TF32, with bounded thread configuration. One float32 input/output is supported. Calls require finite, bounded single-batch NCHW arrays; input and copied output arrays are limited to 4,194,304 float values each. Copy limits do not constrain intermediate native allocations. A failed native call, SDK recheck, input/output check or run-bound check invalidates the session. Receipt creation consumes it, checks the independently supplied expected run count and validates a bounded original-byte CUDA node trace. Trace consistency remains distinct from authenticity and complete runtime/attempt binding.

The CUDA arena is not a whole-device allocation quota. This distinction follows the [official provider documentation](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html) and remains explicit in [resource accounting](PULSAR_GPU_RESOURCE_ACCOUNTING.md). No physical RAM cgroup or cross-process VRAM enforcement is added by this helper.

## Current evidence

The [final receipt](evidence/roadmap-2026-10-01/rust-cuda-session/validation.json) binds 164 production and 110 verification paths to current source archives. The default workspace passes 876 Rust tests, with zero failures and seven ignored qualification cases across 43 suites. Two additional CUDA-feature unit cases pass; the CUDA examples and default workspace binaries/examples build. One current native CPU/preceding-reader compatibility case and 214 structural checks pass. Full JavaScript and native-window gates were not rerun for this increment.

The captured-library namespace uses the held kernel-device gate, a separate read-only SDK declaration and the compiled Rust probe. Host runtime directories are absent. Four calls to the authored 302-byte graph produce 0.25, 0.375, 0.5 and 0.75. Both the wrapper and parent trace reader accept the same original trace digest and twelve CUDA computation events. Reported native-library mappings belong to declared captured aliases. Initial and final campaigns are separate; the initial three-case subject and binaries are retained before adding the failure scenarios.

Five final negative cases refuse: an unavailable logical ordinal, a CPU-only graph, failed native input followed by reuse/receipt attempts, the wrong expected run count and a preinitialized runtime. The CPU-only graph fails explicitly at CPU placement, before the later float32 contract check. The invalid input produces an actual native dimension error; subsequent valid input and receipt creation both refuse. No negative case publishes a checked receipt. Every terminal child leaves an empty capture parent; the successful path also reports explicit close. Negative-path cleanup is independently observed after RAII destruction, rather than rewriting its earlier pending-cleanup record.

The namespace experiment retains a 16 GiB virtual-address limit, 30-second child deadline/CPU limit, 8 MiB per-file limit and 16 MiB tmpfs. It does not measure whole-worker VRAM, enforce a physical RAM cgroup, establish arbitrary lazy-library closure, test cancellation/reset/power-loss, run private media or qualify model accuracy/performance. CUDA SDK total-memory and `nvidia-smi` observations remain distinct.

## Remaining integration

Bind the adapter to owner-approved device/dependency inventory, aggregate reservations and selected profile admission before launch. Carry those captured identities and resource claims into durable GPU attempts, worker receipts, restart/cancellation fencing, compatibility readers and authenticated clients. Then measure actual supported models/media and required performance/platform/device scenarios. Actual confined Rust computation closes this adapter feasibility prerequisite; it does not close B3, Handy or release qualification.
