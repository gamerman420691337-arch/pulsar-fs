# Live CUDA cold-start diagnosis

Native public live CUDA startup remains FAIL. Three diagnostic runs reproduce a failure before Ready: two report Starting at the issued 30-second test deadline; the third reports an expired capture with no completed inference. The test now records invalid-ordinal refusal time, admission time and the observed inference state on readiness timeout. Only test diagnostics changed. No production deadline, resource limit, lease refusal, snapshot or durability policy changed.

Admission completes in 17.64–33.95 ms in these runs. The invalid ordinal refuses in 55.89–71.30 microseconds. The delayed phase is after admission. In the first run, owned test and capture threads show journal-commit waits and completed fsync calls take up to 16.73 seconds. In the second, fsync calls are mostly short, while the capture helper appears in kernel dirty-page throttling in 24 samples taken one second apart. These samples establish observations, not an exact continuous wait duration.

The third run identifies actual blocked copy calls. The capture helper writes to `/capture/native-dependencies-8AqXGh/content/.tmpRxI8hb`, from mounted input `/inputs/4`: the pinned 545,528,240-byte cuBLAS Lt library. Three 8 KiB writes take 13.19, 2.97 and 1.77 seconds. The native library specification declares 74 libraries totaling 1,943,035,224 bytes. Input declarations, actual files, model and NVML identities are rehashed before each diagnostic run.

The source path is `start_live_cuda` → `native_image_reuse.capture_with` → supervised `capture_tracked_in_lease` → native dependency capture → `snapshot_opened_reserved`. First-use native image capture occurs under the already-issued live lease, before memory observation and persistent inference startup. Capturing this large closure under I/O pressure consumes that lease before Ready. This identifies a demonstrated preparation delay in these failed runs; it does not explain every earlier startup failure or establish a native driver/runtime defect. Tracing adds overhead and these runs are not a latency qualification campaign.

A proposed copy optimization was tested and rejected. The existing snapshot passes a temporary-file wrapper to `std::io::copy`, producing 8 KiB userspace writes here. A scratch candidate passes the underlying File: reflink and copy_file_range reject this cross-device path, then sendfile copies the bytes. Both isolated copies produce the exact declared SHA-256, size and read-only result. The existing path takes 23.78 seconds and the candidate 85.20 seconds, including a 78.82-second sendfile. This source-level scratch experiment used a different cached tempfile artifact from the one later resolved for the engine by Cargo. A subsequent probe using the resolved engine dependencies compiled, but an 8 MiB copy exceeded its 20-second observation bound; its trace includes a 14.87-second fsync and an unfinished following fsync. There is no completed comparison with the resolved engine dependencies. These experiments under variable I/O pressure are not engine-build timings or a statistical benchmark and do not establish a general regression. It does not justify applying the proposed optimization. The production artifact implementation is byte-identical to the preceding checkpoint.

The next software work must separate reusable native-image preparation from an active capture lease with explicit ownership, admission and disposal, while preserving fresh live authority, mounted-byte verification and the original capture deadline. Extending the capture lease or reusing an offline job as live execution authority would not address that contract. This preparation change is not implemented by this checkpoint.
