# Checked Windows artifact boundaries

**Private Windows artifact publication remains unsupported. Its helpers now refuse explicitly instead of claiming privacy or durability that they do not establish. Checked read-only artifact access is implemented; native Windows qualification remains UNKNOWN.**

Source inspection found that non-Unix private_directory created directories without ownership/DACL validation and sync_dir returned success without performing a directory sync. The public publish_export could consequently create and publish bytes while reporting successful directory synchronization. The app's Windows server already refuses startup, but library helpers must preserve the same authority and outcome boundaries independently.

Private-directory creation/validation and directory synchronization now return explicit unavailability errors on non-Unix platforms. Snapshot paths, opened-descriptor capture and worker-snapshot reuse refuse before reading/seeking/copying or publishing into an unvalidated store. Export refuses before path lookup, temporary-file creation or destination publication. Existing folders, source bytes and selected outputs are not repaired, removed or silently rewritten. Unix behavior stays on its existing implementation.

Windows open_regular now uses safe Rust read-only opens, FILE_SHARE_READ without write/delete sharing, final-reparse opening and anonymous security QoS. It requires a native absolute filesystem prefix and refuses device/UNC pipe namespaces. Actual held metadata must describe a regular non-reparse file. This permits checked supplier reads and bounded digest verification; it supplies no private-storage, model-execution or publication authority. The [Rust API contract](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html) defines these open options. A successful file flush is not a replacement for checked namespace durability; [Microsoft's FlushFileBuffers contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) describes its handle and access requirements.

The preceding production definitions are compiled with the new Windows assertions in an isolated diagnostic subject. All **three fail**: private-directory creation reports success, an export publishes successfully, and a reader accepts an existing writer. The retained baseline source and executable identities describe this negative subject separately from the restored final working tree. It creates only owned authored RAM fixtures.

The same three checks on the final subject exercise no-effects refusal, exact retained bytes, bounded SHA-256, existing/new writer conflict, hard-link sharing, rename/removal refusal, release after drop, genuine symlink/reparse rejection and namespace refusal. The link must exist, expose the reparse attribute and read the authored source before rejection is counted. This is scoped Windows API emulation under Wine, not native filesystem or whole-Engine qualification. Only the named Windows artifact tests run; the full Windows Engine suite is not substituted by them.

Final scoped Wine verification passes **3 tests, 0 failed, 0 ignored**, with 541 other Windows Engine tests filtered out. It does not claim a passing whole Windows Engine suite. Rebuilt Linux Engine and Clients pass **841/322**, with **70/8 ignored**. Both strict Linux lint configurations, Linux/Windows workspace/all-target checks, formatting, native App/Worker build, 445 architecture checks and 36 source guards pass. Core/Protocol and the 38-executable portable Windows campaign are inherited from their preceding unchanged-source checkpoint and are not rerun here. Windows target warnings remain open. The [checkpoint](evidence/roadmap-2026-10-12/windows-artifact-boundaries/checkpoint.json) retains scoped source/executable identities, both Wine subjects, the first compile typo and final checks; it is not hermetic build provenance. Private Wine prefixes have no display and use RAM/PID/network isolation. Their own servers are waited for; per-run scratch is removed only after known handles terminate and accessible references are checked. Shared caches, toolchains, borrowed assets and unrelated state remain preserved.

Windows private ACL creation/validation, anchored stores and recovery, publication/durability, secure IPC, process confinement and native/MSVC acceptance still need implementation/qualification. This checkpoint does not implement a Windows edition or complete its export workflow. Model/media accuracy, annotations, GPU/device behavior, offline editions, native GUI, packaging/signing/clean-machine and human/release gates remain open. Roadmap remains PARTIAL.
