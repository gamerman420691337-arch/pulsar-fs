# Owned native image preparation

The engine exposes a Linux trusted-host preparation API before capture. `prepare_live_cuda_image` captures or reuses the configured native image under a separate explicit preparation deadline, then returns an owned `PreparedLiveCudaImage`. `LiveCudaImagePreparationOptions` declares preparation and retention milliseconds. The owner-configured preparation maximum defaults to 300 seconds and can be set through `EngineConfig::native_image_preparation_timeout`; individual requests remain within the existing native capture maximum of one hour. This setting does not change `worker_timeout`, a live capture lease or an inference worker deadline.

The method requires a CUDA build and a loaded owner policy, validates declared bounds and cancellation before work, and uses the existing supervised, tracked native capture. Its image specification digest, byte count and engine epoch are metadata; availability means only that this handle retains a verified image use. It creates no model/device/session authority and does not mean GPU inference is ready. Every actual live start continues through its existing current grants, revision, policy, memory observation, mounted-byte and deadline checks.

Preparation reserves retention admission before copying. At most eight preparing/retaining uses can occupy the engine's retention slots. Each watcher claims 512 KiB from the same RAM pool and requests a 256 KiB stack. The watcher retains that reservation and slot until its thread exits; failed RAM admission rolls back the slot. These are admission bounds, not proof of actual aggregate runtime CPU, RSS, deadlines or platform qualification.

The returned handle keeps the native owner alive through the existing weak cache. Its independent retention clock starts only after successful preparation. Explicit release, dropping the handle, or timed expiry removes this use. An active stream borrowing the image keeps its own use and storage custody. Final deletion remains governed by the existing identity-bound staging journal and checked cleanup; expiry is not a physical-deletion receipt. `release` returns whether it removed a use, can report unconfirmed last-use cleanup, and does not claim deletion when another borrower exists or expiry already removed the use.

This is a blocking trusted embedding API. It is not yet exposed as authenticated protocol, CLI, socket or desktop preparation controls; remote callers cannot invoke it. That surface still needs durable intent/status, project/session/revision checks, cancellation, revocation and disposal handling. Existing ordinary live starts retain their cold-capture fallback and can still exhaust their lease under I/O pressure. The full requested user workflow is not complete.
