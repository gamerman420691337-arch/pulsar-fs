# Offline publisher-catalog verification

Status: verifier implemented; [Linux owner-authorized engine/CLI intake and durable snapshots](PULSAR_OFFLINE_CATALOG_INTAKE.md) are implemented. Desktop workflows, current trust/revocation/update and release qualification remain open. This is a prerequisite for GB-10, not completed update trust or release packaging.

`pulsar-engine::offline_catalog::verify` authenticates captured TUF metadata and exact manifest targets against independently approved bootstrap bytes and their SHA-256. It uses pinned `tough 0.24.0`, with its HTTP feature disabled, and a custom in-memory transport. The verifier has no network or supplier-filesystem transport. A caller-provided root digest establishes byte identity; the caller must obtain actual owner approval or a separately authenticated release bootstrap. A root supplied alongside an arbitrary pack does not establish publisher authority.

The [TUF specification](https://theupdateframework.github.io/specification/latest/) treats trusted bootstrap, role thresholds, rotation, expiry and rollback as separate obligations. The [client API](https://docs.rs/tough/0.24.0/tough/struct.RepositoryLoader.html) requires an externally trusted root and persistent metadata for rollback detection. Pulsar retains expiry enforcement and verifies the first root chain from the approved bootstrap, then starts each later refresh from the protected verified current root, with at most 32 updates per refresh. The returned root version cannot fall below the protected prior version. The current signed root plus existing timestamp, snapshot, targets and clock watermarks seed a private temporary datastore. Corrupt or incomplete prior cache refuses before loading; it is never silently reset.

Only nondelegated catalog targets named `manifests/LOWERCASE_SHA256.json` are admitted. Each target must be at most 128 KiB. The entire target stream is consumed and its authenticated length/hash checked before its bytes are used; its exact digest must also match its name. The strict existing model-pack manifest validator then checks the declaration. Publisher signatures cannot admit unsafe paths, invalid contracts or self-qualifying claims. This authenticates declarations only: asset capture, execution closure, rights, runtime compatibility and model quality remain separate.

Raw input admission is 256 captured files, 2 MiB per file and 32 MiB total; names are bounded portable ASCII under `metadata/` or `targets/`, with no traversal, URL escapes or ambient locations. Fetch admission is 256 requests and 64 MiB across all requests, including repeated metadata fetches. Catalogs admit at most 128 manifests. These are raw-byte/count bounds, not measured whole-process memory or latency qualification. Delegations are not supported by this initial adapter.

The caller supplies prior state from protected engine storage. The verifier never writes that storage. Failure returns no successor and leaves prior state unchanged. Success returns all verified manifests, role versions and the complete cache/clock successor for atomic persistence. The temporary datastore is discarded. Unix scratch directories are explicitly 0700. This does not yet establish cross-platform private-storage or power-loss behavior.

Six real-signature Rust cases use ephemeral first-party keys held only in memory. They exercise exact manifest retention, role rollback, bootstrap digest mismatch, missing/corrupt target streams, invalid signatures, expired roles/bootstrap, root rotation with old/new two-key thresholds, duplicate signatures failing quorum, root rollback, repeated rotated timestamp/snapshot refresh rollback, malformed retained state, clock rollback, capture bounds/path refusal and an authenticated unsafe manifest. They do not involve official publisher credentials, private media, installed Stash or Handy.

## Integration and remaining work

1. **Implemented for Linux engine/CLI:** capture local catalog/root bytes through a bounded descriptor-relative adapter after fresh paired-session and model-pack owner authorization. Bootstrap approval must be explicit and distinct from supplier content.
2. **Implemented as one atomic private capsule:** bind a protected catalog namespace to the approved bootstrap and atomically persist the entire successor, including rollback/clock watermarks and verified manifests. Serialize concurrent refreshes and preserve old state on interruption/refusal; never reset watermarks as routine recovery.
3. **Strict protocol reports and CLI implemented; desktop remains open.** Report authentication relative to the approved root separately from official release trust, compatibility, rights, execution approval and qualification. Historical receipts cannot renew current trust.
4. Bind installed pack status to exact authenticated manifest bytes. Define current revocation and explicit rollback semantics for future jobs while preserving accepted jobs and offline owner-approved custom use.
5. Exercise real engine restart/replay, corrupted storage, stale refresh, changed bootstrap, clock rollback and pinned-reader preservation. Complete exact-build notices, executable dependency closure, provider KATs, working Core/Complete artifacts, relocation/platform and independent release gates.

Current database schema 13 and portable format 9 are unchanged. The verifier does not load a native runtime, select a pack, create a generation job, activate an update or authorize physical output. Seven historical qualification cases remain separately tracked.

The initial adapter re-applied the original root chain on every refresh. A reproduced signed-fixture failure showed repeated timestamp/snapshot key rotation could reset newer watermarks. Retaining the verified current root fixes that adapter defect; the initial source/full Rust result and failing regression are preserved separately. This is a Pulsar adapter repair, not a claim of an upstream TUF vulnerability.

The [current source-bound receipt](evidence/roadmap-2026-10-01/offline-catalog-verifier/validation.json) records 847 Rust passes including the six verifier cases, all 93 existing native-configured JavaScript passes without skips, five existing headless pack-panel passes, 208 structural checks and native build/diff checks. Source archives and 24 executable records agree before/after the campaign. These are primitive and regression checks, not production catalog workflow qualification.
