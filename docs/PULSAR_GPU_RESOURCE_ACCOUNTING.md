# Cooperative GPU resource accounting

The engine resource pool now supports explicit per-device budgets and atomic RAM/job/GPU admission. Default engine construction still configures no GPUs, and production inference admission remains CPU-only. [ADR B3-016](../research/phase-b/ADR-B3-016-cooperative-gpu-reservations.md) records the prerequisite.

An owner-configured budget pins a conventional GPU UUID and ordinal, maximum aggregate GPU reservation, capacity retained for interactive work and a positive control-memory floor. Duplicate UUIDs/ordinals and invalid or oversized capacities refuse. Offline reservations cannot consume the retained interactive slice; all reservations share the same total cap. Virtual address space and CUDA arena limits retain their separate meanings.

The broker supplies a monotonic-time memory observation for the exact UUID/ordinal. Future timestamps, observations older than one second, inconsistent free/total values, insufficient total capacity or insufficient free memory including the control floor refuse. Freshness is checked again under the accounting lock before admission. A single mutex commits RAM, job slots and GPU claims together. Storage attachment failures and reservation destruction release the entire claim. Attaching nonzero storage twice now refuses and releases the original reservation; previously it could overwrite the stored amount while leaving aggregate accounting charged twice.

These are process-local cooperative reservations. They do not enforce worker VRAM usage, exclude other GPU users, authenticate observations or authorize character-device access. External allocations can invalidate free-memory observations after admission, and CUDA allocations can exceed a declared arena or reservation. The integrating broker must own observation, device access, scheduling, cancellation and cleanup. Pool restart begins empty; stale execution must be fenced by process supervision rather than reconstructed as authority from this accounting state.

The [read-only native example](../crates/pulsar-engine/examples/gpu-reservation-check.rs) compares a requested UUID/ordinal with host `nvidia-smi` memory metadata, then exercises an offline reservation, refusal of a second offline claim, a preserved interactive claim, release and stale-observation refusal. It executes no GPU inference and supplies no device authorization. Its external harness imposes a process deadline; the example does not promise a standalone timeout for the observation command. Unit tests additionally check competing threads, invalid policies, mismatched observations, RAM refusal and failed/double storage attachment.

[Evidence](evidence/roadmap-2026-10-01/gpu-resource-accounting/validation.json) binds exact source and binaries to these checks. No wire fields, database schema, model bytes, private media, training, sterile evaluation or Handy contact change. Production GPU inventory/owner authorization, device node binding, dependency-set/attempt persistence, selected Rust CUDA sessions and model/platform/release qualification remain open.
