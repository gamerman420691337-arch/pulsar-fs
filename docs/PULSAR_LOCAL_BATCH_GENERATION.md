# Retained local audio batch generation

The explicit local workflow separates immutable intake, generation advancement and publication. `library-batch-prepare FOLDER --audio-bundle-recipe RECIPE.json` discovers pending audio targets using the existing bounded folder selector, validates every destination before source capture, and snapshots selected bytes into Engine-owned storage. The six-axis recipe is retained as checked values. Original media and recipe files are not reopened to reconstruct later generation intent. Existing targets are skipped by discovery and their contents remain unverified; the Engine also refuses any selected destination that already exists at admission.

`library-batch-list` lists only this authenticated session's retained batches, including a preparation reply that was lost before the caller recorded its ID. `library-batch-status ID` reads retained phases without dispatch. `library-batch-advance ID --steps N` explicitly advances at most 1..=1000 generation phases. It creates each project, imports the exact captured source digest/length, submits the shared six-axis audio job, observes its existing candidate and commits at the captured revision. Each mutating phase request is retained before execution. The acknowledgement and outer advance response are committed together; an interrupted acknowledgement retains the outer request ID for exact reconciliation. The CLI uses that retained ID rather than choosing another mutation. Repeating an acknowledged advance replays its accepted response.

The state sequence is selected, project_created, source_imported, generating, candidate_ready and ready_for_publication. No work automatically starts at Engine restart. Current session authority is required for each advance and every inner project operation; bearer tokens are never stored in the batch record. A different session cannot enumerate/read the batch. Source mismatch, changed tool identity, project revision conflicts and unsuccessful/interrupted jobs retain their state and error; no replacement job or implicit migration is created. Ordinary job recovery remains explicit. There is no new batch cancel or migration command. Explicit metadata release is described below.

Generation readiness means committed synthetic neutral motion is available in the retained projects. It does not mean published folder outputs. Use the existing `export-bundle PROJECT DESTINATION --revision REVISION` separately for each ready entry; inspection and exact-intent recovery retain their existing contracts. The batch's publication_completed and qualified fields remain false, including after independent publication. The subsequent [client publication handoff](PULSAR_LOCAL_BATCH_PUBLICATION.md) supplies an independent per-entry publication journal and explicit bounded prepare/publish/status workflow. It does not change Engine publication_completed or provide an autonomous watcher, automatic destination retry or a full roadmap completion claim. The subsequent [bounded scheduler](PULSAR_LOCAL_BATCH_SCHEDULER.md) provides explicit retained per-entry generation/publication advancement. Ordinary batch/scan behavior remains unchanged.

Schema 28 wraps preceding storage reader layers and preserves their independent minimum requirements. Older readers refuse this header. Captured source membership prevents snapshot eviction through an imported source alias. Input/catalog/record capacities are bounded: 1..=100 entries per batch, at most 128 retained batches, one MiB per private record and 32 MiB total record bytes. `library-batch-release ID --request-id RELEASE_ID` removes this session's ledger and source membership for entries that are all selected or ready_for_publication, only when there is no pending inner/outer acknowledgement or item error. Partial generation refuses release. The caller retains RELEASE_ID and repeats the identical command to recover a lost acknowledgement; a fresh request after release refuses. Removal and the retained final-report receipt commit together. Other batches sharing the same snapshot remain pinned. The reader header stays in place. This command deletes no source, snapshot object, project, job, candidate, export record, published bundle or staging intent. It frees retained ledger capacity and this batch's eviction pin, with existing eviction checks still applying. Historical preparation and advance responses remain replayable history and cannot restore the released ledger. Release is neither publication completion nor job cancellation. General snapshot garbage collection and reconciliation/cancellation of partial batches remain open. A failed later input capture may leave immutable content-addressed snapshot objects without a batch record; it creates no generation project or job and performs no broad cleanup.
