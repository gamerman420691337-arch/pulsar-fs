# Native preparation intent custody

The protocol now defines bounded native preparation/retention options and image preparation intent/report metadata. Intent binds the operation, engine boot, owner session, project revision, original request, declared image specification digest, owner-policy digest and byte count. Declarations are limited by the existing eight-GiB native total and one-hour maximum preparation/retention bounds. The trusted Rust preparation API uses these same options and retains its independent owner-configured maximum, defaulting to 300 seconds. These types contain no authentication token, device capability, model readiness or launch authority.

The engine implements a conditional schema-27 reader barrier and bounded SQLite operation journal. Creation, initial report and barrier share the caller's transaction; the transaction must commit before any capture or spawn. Operation ID and owner/original request are unique, exact intent/fingerprint conflicts are refused, reports are canonical and admitted to 16 KiB before deserialization, and retained history is bounded at 4096 records. SQL verifies field types/lengths and indexed/report correspondence. Actor/project/revision membership is validated even independently of SQLite foreign-key enforcement. Actor membership remains historical metadata; it does not replace current authentication, grants or revision checks.

Successors preserve intent and clock correspondence and advance exactly one generation. States also require their minimum possible lifecycle generation; canonical/index-consistent fabricated Retained state at generation zero is refused. Elapsed time records the committed lifecycle event, not a fresh status clock sample. The controller must still compare current time and actual handle availability. Cancellation request prevents a late capture result from publishing Retained, and a stale generation cannot overwrite a newer state. A retained-use timestamp cannot be renewed. Explicit release, expiry and cancellation are distinct states; released/expired/cancelled use does not by itself claim physical deletion. Cleanup confirmation remains false until actual storage retirement is established separately by the resource owner. The journal does not produce such a receipt itself.

Read-only startup validates the new header, exact layouts, canonical bounded records and membership before opening SQLite for writable recovery. Unknown, downgraded, missing-marker, malformed, oversized, inconsistent or noncanonical state fails closed. The outer native-preparation barrier preserves existing portable annotated, portable WASM and WASM archive reader layers during later publication. On restart, all nonterminal intents become Interrupted in one transaction, preserving their declaration and historical retained-use timestamp. Recovery never restores image handles or model/device authority and does not assert staging cleanup. Existing fence/staging journals retain their independent physical resource obligations.

The current engine supports reading and recovering the journal. The begin/advance storage primitives are exercised directly in tests. Ordinary RPC does not create preparation records yet, and the trusted embedding preparation call still executes independently of this journal. Authenticated asynchronous controller creation, durable request resolution/status, active grant/revision rechecks, cancellation/revocation/disposal, and CLI/desktop controls remain required integration work. This is a prerequisite, not completion of the requested user workflow. The unwired arm/begin storage helpers contribute two non-test dead-code errors until that controller integration is implemented.

The [checkpoint](evidence/roadmap-2026-10-10/native-preparation-journal/checkpoint.json) records protocol, selected journal, full engine, build and reader verification. New tests cover transaction rollback, exact declaration/fingerprint replay and conflicts, cancellation/late retention, stale generations, interruption, malformed/downgraded state, preservation of nested reader publication, actual engine reopen and unchanged database/WAL/fence bytes on corruption refusal. A pinned preceding schema21 binary is also run against schema27 with committed WAL: it refuses before mutation or socket creation. The current engine then reopens the same state. No database/authentication files are exported into evidence.

This increment does not run native GPU capture, repair the earlier stale-observation or post-Finish cold-copy failures, train a useful model, evaluate real media, publish to live Stash or actuate Handy. A green library test run is not native/platform qualification.
