# Handy playback coordinator

`pulsar-engine::playback_runtime::HandyPlaybackRuntime` is the engine's conditional Handy HSSP scheduling coordinator. It binds a pending start to the exact project, revision, program artifact, device/firmware/driver/transport/profile configuration, controller, host device-session epoch and host/server clock mapping. It issues sealed, single-use effect intents; it does not perform network calls or authorize client requests.

The owning engine must verify qualification evidence before constructing `QualifiedCommandTiming`, re-read current authority and admission facts immediately before dispatch, and use a fresh host session epoch after process restart. Neither qualification timing nor effect tokens are deserializable client claims. No default command-age, clock-error or drift allowance is provided. Positive timing bounds in tests are synthetic inputs, not measured Handy thresholds. The qualification record must cover actual Handy HSSP curve execution, quantization, transport latency/deadlines and stopping; a profile JSON or successful inspection is insufficient.

Only one start may be pending. Immediately before issuing a play intent, the coordinator checks the complete admission, controller/session, clock domain, monotonic direction, command age and uncertainty. It advances estimated server time by whole elapsed milliseconds, conservatively adding the discarded fraction and the ceiling of qualified drift to clock uncertainty. Start offset, normal playback rate and disabled looping remain unchanged. A rejected current command retires its pending admission and requires explicit rearming. A token from an older pending command cannot consume a newer one.

Effect issuance marks physical stopping as pending before an external transport can act. The engine must send outside the coordinator lock, verify that the effect is still current before transport handoff, and return its exact token with completion. This allows revocation/stop/reconnect processing while transport is in flight. A retired play or stop callback cannot restore authority or change a newer session. An unknown play outcome issues a stop intent and never retries play. A stop already in flight is not automatically reissued by repeated coordinator requests.

Stopping before any play intent has been issued cancels admission without a physical effect. After issuance, cancellation cannot clear physical uncertainty. Stop acknowledgment and unknown stop outcomes both enter `StopUnconfirmed`; neither supplies physical stopping evidence. Only engine-qualified stop observations or valid qualified elapsed-bound facts may clear the pending stop. Evidence intake requires the captured device-session epoch explicitly; it cannot relabel an old observation with the current session. Reconnect discards queued/in-flight host authority, remains disarmed and preserves physical uncertainty. It also loses the previous session's qualification in the core state, so an old elapsed-bound argument cannot certify the new connection as stopped. Separately approved headless playback may continue after controller disconnection; revocation still stops it.

These rules protect host state and prohibit replay. They cannot prove that a remote server will reject an already-sent late play request or that a disconnected physical device has stopped. Actual driver cancellation/order/watchdog behavior and the physical stopping/synchronization evidence remain qualification obligations.
