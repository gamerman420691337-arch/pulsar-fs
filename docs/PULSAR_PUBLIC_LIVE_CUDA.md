# Public live CUDA capture

Linux CUDA-enabled Engines with an explicit matching owner policy now accept a CUDA temporal profile through authenticated `StartLiveCapture` and the existing RGB intake. The capture registry creates the real runtime scope, and an owned scheduler performs private startup, Ready binding, frame-pair inference and provisional completion. It holds the actual worker until cancellation or consuming finalization; a client never supplies an evidence envelope as publication authority. CPU capture behavior and ordinary worker admission remain separate and retain their existing bytes and provider guard.

Public GPU admission checks the declared profile, pinned runtime, owner device/priority and tensor adapter before publishing a capture. GPU RAM admission honors the larger of the Engine worker floor and the declared minimum, bounded by the owner pool; GPU output uses the existing Engine output limit and the declared thread count. Preparation, device observation, native custody and execution still inherit the original capture lease. An unsupported build, missing policy, mismatched device/profile or insufficient budget refuses without CPU fallback.

`FinishLiveCapture` and `pulsar live-capture finish PROJECT REVISION EPOCH --request-id ID` request asynchronous completion. The owner needs Read, ImportSource and Generate grants at the admitted revision. Finish requires Ready completed or in-flight work. Its durable acknowledgement precedes the transition to `FinishRequested`, which clears provisional output and freezes intake, new analysis dispatch and continuation. The scheduler drains any already issued pair without publishing a latest result, then invokes the consuming finalizer. Poll capture status for Completed or another terminal retirement. Replaying the same Finish returns current capture state; it cannot rearm a stopped capture. CPU Finish and foreign-owner/revision/authority requests refuse.

A live capture's minted source is not imported media. Public finalization therefore uses a separate `live_cuda_capture_evidence` table and conditional schema22 barrier. The existing schema21 table and its imported-source foreign key remain unchanged. Capture origin records contain the owner ID, boot, scope, options and originating request ID, never an authentication token. Readback requires canonical bounded origin bytes matching the original initial capture receipt, canonical native controls, original receipt/trace bytes, indexed identities and historical owner/project/revision membership. It does not follow stored paths, load CUDA or reactivate captures.

The new and legacy tables share the existing limits of 256 records and 256 MiB. A 512 MiB memory admission precedes loading origin/native blobs; storage admission covers twice the evidence plus origin bytes and publication overhead through commit. New tables, native bytes and the schema22 barrier commit atomically. CPU databases do not acquire this barrier by being opened. Startup validates layout, bounds, original bytes and origin/receipt correspondence before ledger recovery or writable WAL setup. Older applications refuse the new state. Known old layouts delegate through the checked schema20 base only after validating the actual barrier and both tables.

Final serial verification is retained in [the evidence packet](evidence/roadmap-2026-10-07/public-live-cuda/checkpoint.json): 1,030 workspace tests and 548 CUDA Engine tests pass, with 55 ignored cases in each suite; nine CPU application cases pass without skips. The default build and 265 structural checks pass. The final native public case passes with schema22 offline-generation coexistence and a preceding-reader refusal before database/WAL/ledger mutation. These counts describe local software checks, not roadmap acceptance. Authored tests cover Finish drain/freeze/replay/authorization, provider and metadata separation, CLI grammar, exact CPU bytes, origin/source distinction, storage/receipt/revision/duplicate refusal, rollback, bounds and tampering. Native tests use normal authenticated Engine Start/status/Finish and RGB intake, automatic scheduling and no test-inserted registry. They verify three GPU runs/nine CUDA computation events, report/native-byte linkage, unchanged media-library membership, cleanup, the new reader barrier and Engine reopen. This is an in-process Engine API campaign, not a native CLI/socket or product UI campaign. The schema22 generation follow-up checks normal offline generation after public live completion.

The initial native refusal exposed the CPU-sized output budget still used by GPU admission; production now honors the GPU path's bounded budget rather than weakening profile floors. A later test wrongly reused the larger interactive reservation for offline generation and correctly hit the owner priority ceiling; its correction retains the original offline profile. Failed logs, outputs and captured source subjects remain separate from final passing evidence.
