# Explicit browser recording commitment

2026-10-13. Implemented with scoped native and rendered browser evidence.
Browser gap resolution/export and model/device/human acceptance remain open.

After staging, click **Review candidate diagnostics**. The Client checks the current
candidate's project, base revision and program digest against the diagnostic
snapshot. Commit readiness does not mean useful motion or physical qualification.

Check **Replace the project master with this reviewed candidate, preserving its
remaining gaps**, then click **Commit reviewed candidate**. This is whole-master
replacement through the existing Engine CommitCandidate operation; it is not a
selective axis merge. Existing Engine authority, revision and protection checks
remain authoritative. The page prepares and displays an original commit identity
before dispatch. Preparation changes no project revision. The acknowledgement
reports the committed revision, current revision and remaining gap count.

**Retry original commit request** repeats the same candidate/base/request identity.
Changed approval, missing review, wrong digest and unacknowledged requests refuse.
The Client distinguishes the acknowledged historical revision from current project
state, so replay does not assert that the project has never advanced. No review
disposition, gap fill, funscript export, physical qualification or toy command is
performed by this operation. Existing recording reads retain each capture's original
admitted revision after the project advances.

One staging/commit intent remains retained per finite browser server run. Preserve
its displayed IDs/options for CLI recovery after server loss; server memory is not
a durable recovery store. A null acknowledgement is unconfirmed, not proof of no
effect. Read-only diagnostics may show an old candidate while refusing new commit
readiness if its project or base revision has changed.
