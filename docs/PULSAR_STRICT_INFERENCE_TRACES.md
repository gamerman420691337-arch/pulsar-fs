# Strict native inference trace consistency

`pulsar_engine::inference_trace::validate_node_trace` now checks bounded ORT profiling bytes against an explicitly requested CPU or CUDA provider and an independently supplied run count. This is a production-library prerequisite for the GPU adapter. Enabled production admission and sessions still run CPU; this parser does not enable CUDA or change current execution authority. [ADR B3-013](../research/phase-b/ADR-B3-013-bounded-native-provider-traces.md) records the interface and compatibility boundary.

The parser admits at most 8 MiB, 65,536 events and 16,384 expected runs. Array event count is bounded during deserialization. Supported events are complete `Session` and `_kernel_time` `Node` spans with unsigned integer clocks and process/thread IDs. Clock addition is checked. Every model run must have a positive interval; same-thread runs cannot overlap. Each node must fit one matching process/thread run. Every observed node provider must equal the pin, and each run must contain computation. Known `MemcpyFromHost`/`MemcpyToHost` events are counted separately and cannot substitute for computation. Unknown categories/phases/node events or providers refuse. This supports the observed trace shape, not every ORT release or profiler mode.

The result contains the requested provider, exact run/computation/transfer counts and SHA-256 of the original bytes. It does not authenticate the trace, verify model/runtime/attempt identity, prove absence of unrecorded work or grant qualification. Those bindings and the actual run count remain the caller's responsibility. A forged trace can lie; successful JSON validation is not evidence that execution occurred.

The [read-only native adapter](../crates/pulsar-engine/examples/inference-trace-check.rs) exercises the same function. Unix input uses no-follow/non-blocking open, regular-file/size admission and byte-count/mtime checks. The harness imposes its own process deadline; this example does not supply a standalone filesystem wall-time guarantee.

The [evidence packet](evidence/roadmap-2026-10-01/strict-inference-traces/validation.json) retains 856 Rust passes, seven ignored qualification cases across 43 suites, native builds and structural checks. Twenty-two native reader cases include three previously recorded CPU/CUDA traces, mixed provider, missing/overlapping runs, missing computation, orphan nodes, malformed/overflowing clocks, malformed/oversized input and FIFO/symlink/directory refusal. Those three positive cases are validation of retained bytes, not new GPU execution. A separate fresh authored four-run CUDA probe passed both its numerical oracle and this Rust validator, with twelve CUDA computation events.

## GPU memory contract requirement

At the trace checkpoint, the launcher applied `ResourceBudget.memory_bytes` both to the physical-memory cgroup and `RLIMIT_AS`. The subsequent [CUDA resource contract](PULSAR_CUDA_RESOURCE_CONTRACT.md) separates the launch arguments while preserving current CPU limits; CUDA admission remains disabled. An authored host CUDA probe with `RLIMIT_AS=1610612736` refused during dependency loading: `libnccl.so.2` could not map a segment. No success or CUDA inference is claimed for that attempt.

A fresh unconstrained host probe was observed through its own `/proc/PID/status`. Across 393 samples, observed kernel high-water values reached `VmPeak=7463064 KiB` and `VmHWM=619116 KiB`. These are sampled running-process high-water observations, not guaranteed terminal peaks, whole-worker VRAM measurements or representative model benchmarks. The C++ source/runtime/model are identified in the preceding [CUDA probe packet](evidence/roadmap-2026-10-01/cuda-runtime-probe/validation.json); current artifacts retain the fresh trace and reader result.

The GPU contract must distinguish physical RAM, virtual address space, device-memory reservations and the CUDA arena setting. Raising the existing memory field would also change the physical admission limit and cannot serve as a silent workaround. CPU limits remain unchanged. GPU dependency capture, explicit device/confinement admission, aggregate scheduling, strict selected sessions, bounded termination, measured model/provider behavior and platform/release acceptance remain required. See [CUDA feasibility](../research/phase-b/cuda-adapter-probe-2026-10-04.md).
