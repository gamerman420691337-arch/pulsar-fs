# Live preparation: verified blocking-read deadline gap

The persistent live worker checks cancellation and its absolute deadline between snapshots. A snapshot can block inside an individual filesystem read or sync, preventing those checks from running. The admitted preparation implementation now passes controlled native deadline, cancellation, ownership and normal-execution cases. The declared current-source software gates passed; whole-path and release qualification remain open.

The [controlled native evidence](evidence/roadmap-2026-10-01/live-staging-io/validation.json) uses the actual compiled live-inference fixture, worker, runtime and authored model. A private read-only FUSE file serves the original model bytes and holds its read until an owned release marker is created. No model bytes, profile, physical device or production source were changed.

Two held-read runs on RAM-backed scratch reached the model read in approximately 0.4 seconds, but the preparing caller remained blocked after its five-second budget plus 1.25 seconds of observation margin. A further held-read run on executable RAM-backed scratch reproduced the same result. The caller was waiting in `fuse_chan_send` and returned `live staging deadline exceeded` only after the read was released.

The same executable scratch filesystem with the read released from the beginning completed successfully in approximately 0.53 seconds, produced three estimates, reused one model process and confirmed process retirement without physical dispatch. This isolates the read hold as a sufficient cause of the preparation overrun. An initial disk-backed probe never reached the controlled model read and is retained as inconclusive. These experiments do not prove that this gap caused the earlier four full-application failures.

All five owned FUSE mounts were unmounted and their servers reaped. Each controlled RAM-backed run removed its snapshot scratch only after the owned fixture exited. The original disk-backed failure state remains private. All 308 current production/verification source records still match the preceding runner-capture subject. The native helper and model/runtime/worker identities are recorded in the packet.

The reusable debug command is `held-read.sh AUTHORED_INPUT REPORT TMP_BASE [held|released]`; its source and the filesystem fixture source are archived in the packet. A held run returns exit 1 for the verified deadline gap, exit 0 for a timely return, and exit 2 when the controlled read was not reached. Production GPU admission and media/model, Handy, platform, human and release qualification remain open. See the [implementation plan](PULSAR_LIVE_STAGING_IO_PLAN.md).

The implementation moves trusted byte copying, hashing, source descriptor selection and sync into an admitted preparation task. The caller independently observes the original cancellation and deadline. An opaque prepared bundle owns its private directory, reservation and bound engine scope; lost or late replies initiate independent cleanup. Cleanup failure or inability to start cleanup retains ownership instead of releasing capacity. The confined model worker starts only after timely preparation and uses the existing worker custody. This task executes no model/runtime code. Whole-process CPU/RAM enforcement, durable orphan recovery and other host-I/O boundaries remain independent limitations. The five changed source paths and 310 archive/live readbacks are retained separately; the workspace build passed. The full application campaign passed all 108 cases without skips and preserved all 33 executable/metadata identities. The current software gates passed: 940 workspace tests (23 explicitly ignored), all 493 enabled native engine cases, and 478 CUDA-feature tests (17 explicitly ignored). Structural checks passed. These results do not enable production GPU inference.

## Rebuilt native results

The [implementation native packet](evidence/roadmap-2026-10-01/live-staging-io/implementation-native-validation.json) binds the rebuilt worker and both native examples to 310 unchanged archived source records. The workspace binaries/examples build exited 0. The controlled held read reached preparation at 465 ms; its caller returned at the original 5,000 ms deadline while admission and 631,422,752 storage bytes remained claimed. No inference worker started. After producer release, the example confirmed capacity and storage release following cleanup.

Cancellation at 1,000 ms returned at 1,005 ms with the same ownership retention and confirmed cleanup after release. The released-read control completed at approximately 647 ms, produced three estimates through one confined CPU model process, and confirmed process retirement. All three owned mounts were unmounted and their servers reaped. Nine resource tests passed, including failed storage attachment retaining existing custody. These results prove the controlled blocked-read behavior; they do not prove cleanup-failure recovery, engine-crash orphan recovery, or every host-I/O boundary. Earlier failures remain archived and are not retrospectively declared fixed.
