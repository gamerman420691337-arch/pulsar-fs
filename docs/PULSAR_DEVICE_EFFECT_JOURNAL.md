# Durable device-effect metadata and restart recovery

The engine now opens a private `device-effects/journal.sqlite3` at startup with a fresh boot epoch. This is an independent version-1 metadata store; project schema and portable-package formats are unchanged. The current engine still rejects public physical playback commands. No real device effect has been submitted by this implementation or its tests.

`HandyPlaybackRuntime::dispatch_start_durable` verifies and encodes a pending start, then commits its exact effect metadata before returning an intent for transport handoff. A preparation failure returns no play intent, retires that in-flight play and leaves `StopUnconfirmed` with physical uncertainty. An explicitly authorized stop remains possible. The separate low-level conditional coordinator API does not persist by itself; the owning engine must use the durable path for actual start handoff. The physical dispatcher is not implemented yet. [Durable stop handoff](PULSAR_DURABLE_STOP_HANDOFF.md) now pairs every conditional stop origin with a committed receipt and checks exact callback correspondence; no physical dispatch is enabled.

Each journal record retains the boot and device-session epochs, sequence, complete revision/program/configuration admission, controller captured at effect issuance, qualification-record identity, operation kind and request-byte identity hash. These facts are immutable within the sealed effect. A later controller revocation cannot change the prepared effect's identity. Credential values, source media, prompts, hosted URLs and full command bodies are not stored.

The journal uses SQLite full synchronization, immediate transactions for prepare/completion, a single boot-owner row, content-bound record IDs, an 8 KiB record ceiling, at most 1,024 records and history pages of 1–128 entries. These are local metadata resource limits, not physical safety thresholds. Existing records are not deleted to make space. A full store refuses a new start handoff and preserves uncertainty. Retention/archival maintenance remains future work.

Reopening with a new boot epoch fences previous journal handles. A delayed old writer cannot prepare another effect or change a completion. Outcomes distinguish prepared-without-result, acknowledged and unknown. Repeating the exact completion is idempotent; replacing one terminal outcome with another requires reconciliation and is refused. Record integrity is checked before history delivery or completion updates. Unsupported versions, malformed table layout/owner state, corrupt records and oversized records are refused. Unix files must be regular, unlinked to another path, private and owned by the engine user; new files are mode 0600 under a private directory. Independent platform qualification remains open.

Recovery does not replay journal records. `DeviceSession::recover_unconfirmed` and `HandyPlaybackRuntime::recover_unconfirmed` create a disarmed session with physical stopping pending, without restoring controller, admission, headless approval, clock mapping or session qualification. This remains true even for a saved successful acknowledgment. The fresh device-session epoch must receive new engine-qualified physical stop evidence before manual admission. An old session's observation or elapsed-bound argument cannot certify the recovered session as stopped. A saved journal outcome is not an independent physical observation.

The engine's journal startup/fencing path is integrated. Actual qualified device registry/session reconstruction, physical-effect command authority and transport handoff, full outcome reconciliation/retention, qualified evidence intake and physical stopping remain open. Tests exercise conditional synthetic runtimes and private databases, including interrupted prepared starts, acknowledged/unknown outcomes, old-writer fencing, failed preparation, capacity, immutable facts after revocation and corruption refusal. These are software recovery checks, not a device crash/stop qualification experiment.

[Observed stop completion reconciliation](PULSAR_STOP_COMPLETION_RECONCILIATION.md) now retains the exact checked callback outcome in an engine-owned sealed object after a failed completion write. Explicit persistence retries only that historical metadata under the original receipt/boot and cannot issue a device effect or clear stopping uncertainty. Process restart cannot reconstruct this object from a prepared row; comprehensive historical reconciliation and retention remain open.
