# CUDA resource declarations and launch limits

Pulsar now accepts a structural version-2 CUDA profile with separate virtual address space, device reservation and CUDA arena declarations. Production adapter admission still refuses CUDA. This prerequisite does not grant GPU access, load supplier libraries or qualify a model. [ADR B3-014](../research/phase-b/ADR-B3-014-explicit-cuda-resource-declarations.md) records the boundary.

`CudaResourceLimits` declares `device_ordinal`, a conventional `GPU-` UUID, `address_space_bytes`, `device_reservation_bytes` and `arena_limit_bytes`. Ordinals are bounded to 0–63; UUID syntax is checked without claiming device existence. Address space must cover the declared minimum physical RAM and actual admitted RAM, and cannot exceed 1 TiB. Reservation is positive and at most 1 TiB; the arena is positive and cannot exceed the reservation. These are structural checks. There is no device discovery, ownership, measured capacity or aggregate reservation implementation in this change. MIG identities are unsupported.

Version 1 retains its existing resource semantics and serializes without the optional field. Version 2 requires CUDA and explicit resources. Other version/provider/resource combinations refuse. An old strict reader rejects the new field; current production admission rejects the unsupported provider before durable job creation. Stash batch start and migration now preflight profile support before discovery or durable ledger changes. This closes an earlier direct-file batch path that could retain unsupported intent before generation rejected it. Historical version-1 batch intent remains readable.

The launcher has a separate address-space argument for `RLIMIT_AS`; physical cgroup RAM continues to use `ResourceBudget.memory_bytes`. CPU generation and live source/inference pass the same limits as before. The GPU resolver can compute the separately declared virtual limit, but the existing CPU-only adapter check prevents a CUDA launch. `ResourceBudget` wire fields, database schema and portable format are unchanged.

The device reservation is a proposed cooperative scheduling amount, not a hardware-enforced total VRAM quota. The arena covers CUDA EP allocations only. Neither may be advertised as total worker GPU memory control. Future enabling work must capture and verify native dependency closure, authorize and confine the exact device, implement aggregate reservations and cleanup, bind actual strict node traces and resource observations to attempts, and qualify model/provider behavior.

[Evidence](evidence/roadmap-2026-10-01/cuda-resource-contract/validation.json) records the exact source and native checks. No private media, training, sterile evaluation or Handy contact was used for this change. The prior [trace memory observation](PULSAR_STRICT_INFERENCE_TRACES.md) explains why virtual address space must be distinct from physical RAM.
