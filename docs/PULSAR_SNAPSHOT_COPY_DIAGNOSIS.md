# Executable snapshot copy diagnosis, 2026-10-09

Status: controlled copy evidence recorded; startup reliability unresolved; roadmap PARTIAL.

The production fallback copies a bounded source descriptor into a NamedTempFile, syncs it, and then hashes the captured bytes. A throwaway Rust probe uses the installed tempfile implementation and the current 630,105,268-byte development executable. It compares the original wrapper writer with its underlying File writer. It excludes FICLONE, hashing, permission changes, publication, and Engine startup; it is not an end-to-end startup gate.

Summary-only syscall tracing confirms the wrapper uses 76,919 writes and 76,924 reads, while the File variant uses a failed cross-filesystem copy_file_range followed by sendfile. Two untraced single-copy comparisons do not favor the File variant. At ten concurrent copies, the wrapped driver times out at 90 seconds before running its File phase. A separate File campaign records ten individually killed and reaped 90-second timeouts. The original wrapped failure does not record every individual child result. These negative results remain retained.

A subsequent stage-instrumented four-copy sample completes both variants. Wrapped copying takes 20.52–20.94 seconds and total copy plus sync takes 22.44–22.63 seconds. File copying takes 10.10–10.33 seconds and total takes 10.81–11.11 seconds. This sequential, uncontrolled host sample does not establish a repeatable speedup or overturn the ten-copy failures. Both variants repeatedly wait in balance_dirty_pages_ratelimited_flags.cold. Wrapped final-stage samples also show filesystem/queue waits. The mount is ext4 rw,noatime, without a sync option; host dirty/background thresholds are 256/64 MiB. The inherited cgroup hierarchy has no explicit io.max, cpu.max, memory.high or memory.max cap. No scheduler, threshold, cgroup or service setting was changed.

The measurements locate substantial delay in copying under writeback throttling. They do not isolate why host writeback is slow or prove that a code optimization resolves Engine startup. Production copying, byte verification, storage reservations and deadlines remain unchanged. All 413 records in the preceding source manifest are checked and unchanged. No source build or product test is replaced by this probe.

The [evidence packet](evidence/roadmap-2026-10-09/snapshot-copy-probe/artifact-manifest.json) retains probe sources, compile results, timings, syscall summaries, cgroup context, live process wait/I/O/file-size samples, failures and cleanup metadata. All recorded stage children are terminal. The owned probe directory and 23 generated files are removed after checking ownership, file type and visible process references; 10,011,348,992 allocated bytes are recorded. Eight same-user process FD rosters were inaccessible, a stated observation limitation. Shared build caches are preserved. Prior cleanup/import recheck evidence remains in the separate owned-failure-scratch-cleanup packet: the fresh ten-import test still failed after disk cleanup.

Next work: test bounded coordination of executable snapshot preparation against the actual concurrent startup failure, with explicit cross-process ownership and unchanged byte-verification and deadline requirements.
