# Durable desktop WASM cleanup recovery

Status: bounded software/controller increment and actual IPC PASS; roadmap PARTIAL. Saved cleanup facts are not authority and do not schedule removal or execution.

Before dispatching a removal, Pulsar durably publishes the exact cleanup request ID, owning project, attempt, original start request, observed unsuccessful state and base revision. The private journal is bound to session, credential digest and endpoint digest. It stores no bearer credentials, owner proof, executable/module/input/output bytes, paths or execution approval. If publication or validation fails, dispatch does not occur. A checked removal response publishes an acknowledgement fact; acknowledgement-publication failure leaves the original request available for explicit retry.

A fresh controller loads journal entries as inspectable facts. It restores neither pending execution nor pending cleanup, selected attempt, draft or approval. The user explicitly retries a saved unknown cleanup in its owning project; that installs the original in-memory removal intent and sends the exact original command/request ID. The engine rechecks current authority and uses its remembered response for an already completed removal. A catalog that omits the attempt never acknowledges cleanup by itself. Only a response matching attempt, original start request, unsuccessful state and observed revision can settle the journal. Acknowledged local records can be explicitly dismissed without changing engine work, candidates or the independent start journal. Unknown records cannot be dismissed.

The shared Unix private-storage implementation enforces owner-only directories, single-link 0600 regular files, no-follow handle opening, nonblocking lock/inode checks, atomic replacement with file/directory syncing and a 1 MiB serialized-document bound. The cleanup journal admits at most 64 records and 16 KiB per intent. A changed intent under the same request ID refuses; a second unknown request for the same project/attempt refuses and asks for original-request retry, including across windows. Changed endpoint/credentials/layout, invalid observations, malformed/oversized storage, symlinks and unsafe permissions preserve the original data and refuse. Non-Unix private storage explicitly remains unsupported. These are not hard filesystem-preemption or power-loss qualification claims.

The full client suite passes 169 tests with four default-ignored qualifications. Five cleanup-journal cases cover restoration without authority/bytes, namespace and exact-intent binding, competing cleanup requests, acknowledgement/dismissal correspondence, unsafe/corrupt storage, capacity recovery and concurrent-window writes. Ten panel cases include an explicit check that restoration creates no pending operation or approval. Both application configurations and the qualification-host build pass; 325 architecture checks, 36 source guards and scoped formatting pass. Existing engine warnings remain 37.

The explicit native fixture runs real authenticated control/bulk IPC and a real authored WASM worker. After a verified unreachable guest failure, it writes cleanup intent, makes journal permissions unsafe and proves that dispatch refuses with unchanged journal bytes and both original operations still present. It restores permissions, executes engine cleanup while deliberately skipping local journal acknowledgement publication, constructs a fresh client/controller and loads the exact unknown record. An absent catalog does not settle that record. Explicit original-ID replay retrieves the checked remembered response, publishes acknowledgement and permits local dismissal. The completed original candidate, master motion/revision and both independent start-journal entries remain intact. The fixture took 1.62 seconds; this is an authored acknowledgement-gap scenario, not an OS process-death, GUI event, device or performance campaign.
