# Persistent runtime custody in a Linux AppImage

Pulsar now builds an actual single AppImage candidate and installs verified contents into a persistent private cache before starting the application. The Engine survives closure of its originating client; its later workers and media/native runtimes therefore need persistent paths after AppImage temporary extraction or mounting ends.

The builder is scripts/create-linux-appimage.mjs. It takes four absolute paths: a schema-1 candidate directory, the pinned official appimagetool, the pinned downstream type2 runtime and a new destination AppImage. The original official runtime is historical; current runtime source/pin and verification are in [the cleanup follow-up](PULSAR_APPIMAGE_CLEANUP.md). It streams declared hashes, copies only the finite payload inventory and retains original manifest bytes. It passes the explicit runtime file to the builder, synchronizes output and atomically publishes without overwriting an existing image. The tool/runtime pins are in [ADR B3-105](../research/phase-b/ADR-B3-105-persistent-appimage-runtime-custody.md); upstream sources are [appimagetool](https://github.com/AppImage/appimagetool/releases/tag/1.9.1), [type2-runtime](https://github.com/AppImage/type2-runtime/tree/8f39b89e2ac31e1640b3d3f7e9a5108e6ce805fa) and [AppImage architecture](https://docs.appimage.org/reference/architecture.html).

AppRun calls runtime-launch SOURCE CACHE_ROOT -- ARGUMENTS before Engine configuration. Set PULSAR_RUNTIME_CACHE_ROOT to choose an absolute cache root. Otherwise AppRun uses XDG_CACHE_HOME/pulsar/runtime or HOME/.cache/pulsar/runtime. Missing cache components are created privately through no-follow descriptors. Cache preparation holds a private nonblocking lock; simultaneous preparation reports busy instead of sharing an incomplete installation.

Each original manifest SHA identifies a separate installation. First use calls the existing [offline installer](PULSAR_OFFLINE_RUNTIME_INSTALLATION.md). Every reuse checks the exact manifest/receipt, complete finite inventory, private directories, admitted file ownership/modes/link counts/device and all payload identities. Damaged or unknown contents refuse execution and remain available for inspection. Existing entries are never repaired, overwritten or deleted. Interrupted unpublished installer stages retain [explicit recovery](PULSAR_RUNTIME_STAGE_RECOVERY.md); incomplete cache/lock creation and automatic cache/opaque-temp cleanup remain open. Between-operation deadlines do not interrupt blocked kernel filesystem calls.

The cached application removes transient AppImage location variables before execution. Owner configuration, state roots and explicit runtime/model choices retain their existing semantics. Help, version and completions now run before state or worker discovery. No network download, inference service, model activation or assistant inference approval is introduced by packaging/first use.

The [checkpoint](evidence/roadmap-2026-10-11/runtime-first-use/checkpoint.json) binds exact source/build/tool/native/artifact observations, including any failures. The AppImage process campaign uses extract-and-run with disabled network, an isolated persistent cache/state and authored model/media. The pinned runtime returns success but leaves the extracted payload in this campaign. The fixture explicitly removes its own extracted contents after AppImage parent exit, then proves survival of the cached Engine and subsequent confined worker generation/export. Automatic extract-and-run cleanup is a failed/open delivery gate, not a passing result. This establishes scoped packaging custody, not learned model quality or broad platform qualification.
