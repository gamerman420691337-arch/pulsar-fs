# Shared native capture custody and image handoff

Status: PARTIAL. The real standalone capture caller now uses shared worker custody, and a private tracked constructor verifies committed engine ownership admission and uses durable staging/admitted creation. Verification passes 973 workspace tests (48 ignored), 511 CUDA-feature tests (42 ignored), explicit native capture/handoff/retirement and creation cases, nine native capture inspection scenarios plus direct-role refusal, four shipped-engine staging/portable cases without skips, builds and 243 structural checks. All 324 archived/live source records match. The final image-owned lease assertions execute in both default and CUDA-feature native test binaries; production and all executed broad-suite cases remain identical to the archived broad-gate subject. Production GPU jobs still refuse before capture, so this is not production GPU integration. See [ADR B3-045](../research/phase-b/ADR-B3-045-native-capture-worker-image-handoff.md) and the [terminal checkpoint](evidence/roadmap-2026-10-07/native-capture-custody/checkpoint.json).

Native capture no longer has a separate child/cgroup reaper. Preparation keeps claims and staging installed through raw helper creation failure; tracked creation consumes those owners through the admitted creator. Shared worker custody is installed before command construction and spawn, owns the actual child, and retains failed or cancelled work until child exit, transport retirement, group emptiness and cleanup are observed. Existing standalone capture remains explicitly untracked; the new tracked constructor requires the caller's held engine fence, an independently observed committed schema-20/minimum-4 binding, matching scope and exact canonical state directory. It never opens a separate helper scope inside an engine's state. This is an ownership barrier; the constructor does not authorize a model/provider, reserve an offline scheduling priority, observe GPU capacity or admit a GPU job.

A consuming worker-to-staging handoff handles successful capture. It confirms every byte user retired and acknowledges exact group retirement/reclamation before removing worker custody. Errors leave the normal shared cleanup/reaper owner installed. After success, CPU/RAM/worker claims release while the captured image remains charged to storage. The reservation partition moves only storage ownership without changing aggregate accounting; it never frees CPU or GPU capacity itself. Retained staging carries that storage charge until deletion and any durable journal clear are acknowledged. The image owner disarms the redundant nested-directory destructor and delegates all deletion to its encompassing staging owner.

Native cases exercise an actual confined worker with authored non-library bytes under a committed engine lease, independent byte readback, refused uncommitted admission, released full worker RAM, empty group/creation rosters with one remaining staging obligation, blocked image deletion with retained storage/lease, wrong-byte failure cleanup and same-scope engine reopening. A separate failed-handoff case keeps a transport thread alive after its child exits; timeout retains authored bytes, worker/storage claims and the lease until that thread actually retires. The strengthened case also drops the engine while a successful image remains owned, blocks deletion, observes retained storage and refusal of a fresh engine, then restores deletion and reopens the original scope. The added assertions are isolated to this ignored native case after the broader gates, with [explicit source correspondence](evidence/roadmap-2026-10-07/native-capture-custody/post-broad-gate-changes.json). Preceding native retirement and all fourteen ordinary/encoded-source creation cuts remain separate affected regressions. All 74 original library files retain their hashes across the full capture campaign; the measured full capture took 3,140 ms and deadline/cancellation returned at 252/252 ms, individual observations without a qualified latency distribution. The current-source legacy orphan counterexample still fails with exit 101.

Initial compilation exposed the extracted retirement helper's result type and recursive generic retention composition; the helper retains its boolean retry observation, and recursive cleanup now erases retention at the recursion boundary. The generic retry's raw log was inadvertently overwritten; its source and compiler type artifact remain, and [the failure notes](evidence/roadmap-2026-10-07/native-capture-custody/initial-failures.json) explicitly record that evidence limitation. The first native handoff fixture refused before creation because its temporary root depended on umask; explicit mode 0700 corrects the fixture. Its complete source archives and failed gate log are retained under first-gates/. No permission requirement was relaxed. The first application run then found the inspector treating zero storage as simultaneous CPU retirement after a wrong-hash failure. The corrected inspector and engine regression observe both storage cleanup and worker-capacity release within the original cleanup deadline; the failed subject and raw application output remain under second-gates/. That prematurely exited inspector is not successful cleanup evidence.

This work does not establish a bounded host-filesystem IO distribution, reboot/root relocation or legacy orphan recovery. The tracked constructor is exercised through a real engine fixture but still awaits a production GPU caller. That caller must bind owner policy, fresh device/resources, captured image and mounted-device integrity, actual inference/results, cancellation and restart. Model quality, real-media/physical Handy, platform, human and release gates remain open.
