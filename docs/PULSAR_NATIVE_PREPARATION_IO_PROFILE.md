# Native preparation I/O profile

The production SessionClient native campaign now passes twice on the unchanged implementation and pinned inputs. Both runs complete retained-image preparation, matching Start replay/original-request resolution, two retained uses of one image, release preserving the other use, three authored GPU estimates, Finish under the original 30-second lease, and both cleanup receipts. This verifies the exercised native protocol path and ownership behavior under these runs' conditions. It does not erase the preceding deadline failure or qualify useful model quality, hardware playback or load-independent latency.

| Campaign | Result | Whole test | First preparation observed Retained |
| --- | --- | --- | --- |
| Initial production transport | FAIL | 273.69 s | Not reached; original 180-second deadline refused |
| Cgroup sampling | PASS | 65.68 s | 39.864 s |
| Cgroup sampling plus corrected syscall tracing | PASS | 129.22 s | 99.696 s |

Each new run rechecks the 77 native/model/worker input identities. Preparation remains 180,000 ms, retention 300,000 ms and the live lease 30,000 ms. No production code, memory limit, scheduling policy, snapshot durability or deadline changes were made. The integration source is unchanged from the preceding native-process checkpoint. Synthetic ONNX/gray RGB exercise actual GPU execution without providing accuracy, reference-script or media-quality evidence. The earlier cold post-Finish generation case remains intact and unqualified by this campaign.

The first sampler observes the capture cgroup at its 1 GiB memory ceiling: peak sampled memory is 1,073,737,728 bytes, with 6,650 maximum-limit events and no OOM, OOM kill or CPU throttling events. Reported memory-pressure total is 109,493 microseconds; I/O-pressure total is 15,993,496 microseconds. Last sampled capture CPU usage is 2,740,984 microseconds across a 37.89-second sampled span. Wait-channel samples include dirty-page throttling, folio waits, ext4 allocation/journal work and journal-commit waits. These are discrete observations, not exact continuous wait durations. They show memory reclamation and I/O waits during a successful bounded capture; they do not establish the cause of the earlier failure.

The initial syscall attachment filter mistakenly looked for `pulsar-worker`; the capture process reports `pulsar`. It attached to no process. The cgroup data and native PASS remain valid, but no syscall coverage is claimed for that first run. The corrected second sampler attaches only to the native capture process in this run's own 1 GiB cgroup. Read/write arguments are raw numeric addresses and counts; payload buffers and authentication data are not recorded.

The corrected trace contains 296,717 completed reads, 237,020 completed writes and 224 completed fsync calls. Summed time in completed calls is 2.322086 seconds for reads, 56.927689 seconds for writes and 31.507311 seconds for fsync. One 8 KiB write blocks 22.046479 seconds; another blocks 9.227773 seconds; one fsync blocks 21.628593 seconds. The trace confirms that writes and synchronization consume substantial preparation time in this passing run. Tracing adds overhead, and these summed syscall observations are not a statistical performance benchmark or a proof of the previous failure's root cause.

The protocol's 1 GiB capture ceiling and independently admitted RAM/storage remain intact; increasing a cap, changing global kernel routing or replacing byte proof is not justified by these measurements. Native path completion is now observed, while startup reliability under load, stale GPU observations, cold post-Finish behavior, actual desktop rendering, reference-model/media quality, live Stash, Handy firmware/keys and physical stop/sync, platform/release and human acceptance remain open.
