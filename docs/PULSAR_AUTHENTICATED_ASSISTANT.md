# Authenticated local-assistant proposals

Date: 2026-10-10. Status: **PARTIAL application delivery; authenticated asynchronous proposal execution implemented on Linux; full roadmap INCOMPLETE**.

## Current request path

The shared protocol now has AssistantProfiles, StartAssistant, AssistantStatus, CancelAssistant and ListAssistantAttempts. Profiles contain exact worker/runtime/model identities, fixed owner thread/deadline/memory limits and an opaque Engine-issued ID. A trusted host registers at most eight profiles through `Engine::register_assistant_profile`; this lifetime-scoped native exception contains the host paths privately. Client requests contain no paths, system context, offered IDs, native command or effect authority. Registration expires at restart and is not a bundled/default model decision or a public owner-setup UI.

Start selects one exact registered declaration, submits at most 4,096 bytes of user text and requires authenticated Read plus Edit grants and a current project revision. Engine builds its own context from current project/revision/master metadata. This first adapter offers future generation sample strides 1 through 64. It offers no observed target, review or edit recipe yet. Model proposals cannot change settings, master motion, protection, evidence or devices. A later [explicit generation approval path](PULSAR_ASSISTANT_GENERATION_APPROVAL.md) applies a completed stride proposal to an ordinary generation job with independent Read/Edit/Generate and fresh-context checks. Target/review/edit adapters and their protected action broker remain required.

Accepted attempts and original request receipts commit before dispatch. The original request ID is globally fenced against changed content/other commands. Exact retry returns its original accepted receipt, even after a terminal outcome or profile withdrawal; status and listing return current observations. Global retention is bounded to 128 attempts, with active starts additionally bounded by owner max_jobs. Catalog exhaustion refuses instead of silently deleting history. Removal/archival and unknown-start resolution are not implemented for assistant attempts yet.

Execution uses the [sealed Engine parent](PULSAR_LOCAL_ASSISTANT_PARENT.md), shared admission and durable process-tree custody. Authorization, revision and Running state are checked again before execution; current authority/revision and original execution identities are checked before publishing Completed. Cancellation and session revocation commit their metadata/receipt before signalling the captured exact handle. Host profile withdrawal commits matching unfinished cancellations before removing the profile and signalling; other profiles and completed observations remain intact. A late proposal cannot overwrite a cancelled or stale attempt.

Completion-write refusal preserves the bounded in-memory result and worker handle. A later assistant observation retries metadata publication only; it never reruns inference. While publication still refuses, observation returns Unavailable. Restart changes retained Running records to Interrupted and does not restore profiles, replay inference or presume completion. The read-only startup probe checks the exact SQLite declaration and typed record/column identity before writable recovery. Comprehensive corrupt-cell size/fault/power-loss qualification remains open; private storage is not a hard preemptible I/O boundary.

Both client response adapters validate report structure, owner/project/request/attempt binding, original start profile/revision, state/proposal coherence and catalog limits; SessionClient also rejects duplicate catalog IDs. The CLI/desktop assistant controls and owner configuration/packs are still pending. No installed Python or new native client dependency was introduced. Existing wire fixtures remain separately checked; these are additive command/response types, not permission for old clients to invent support.
