# First-party offline runtime installation

Pulsar provides runtime-install SOURCE NEW_DESTINATION on Linux x86-64. SOURCE may be a candidate directory or a [single-file offline runtime archive](PULSAR_OFFLINE_RUNTIME_ARCHIVE.md). Both paths must be absolute and avoid symlinked components. The destination parent must already exist, be owned by the current user and not writable by other users. The destination must be new; a working installation is never overwritten.

The executable handles this command before Engine configuration. No HOME, PULSAR_STATE_DIR, inference service or network is needed. Installation copies declared candidate contents only; it does not create an assistant policy, select a generation model, copy credentials, initialize Engine state or load a native runtime.

The supported schema-1 runtime-candidate manifest is captured within 64 KiB, must have qualified:false and must declare exactly the known media/application/worker files plus any corresponding assistant and CPU-runtime groups. Unknown/duplicate/traversal records and unknown manifest fields refuse. Input bytes are read through held no-follow directory descriptors. Hashing/copying uses a 64 KiB buffer with exact length, SHA-256 and stable metadata checks. Existing manifests keep their original bytes. This is declared-byte integrity, not signature, license or useful model qualification.

All payloads are written and synchronized inside a new private stage before atomic no-overwrite publication. Existing files never change. The final directory and generated nested directories are private; executables receive0755 and other payloads0644, independent of a restrictive umask. Final parent-sync failure reports that publication occurred with uncertain durability rather than returning success.

A killed installer can leave an unpublished .pulsar-runtime-stage-* directory in the chosen parent. Retry uses a new stage and does not silently remove the abandoned one. The [stage recovery commands](PULSAR_RUNTIME_STAGE_RECOVERY.md) now inspect and explicitly discard recognized inactive stages while refusing live locks and unexpected contents. Legacy unmarked/corrupt stages remain for manual inspection. Automatic first-launch extraction, update/rollback policy, signed packages and broader filesystem fault recovery remain open. The between-operation ten-minute deadline does not interrupt a blocked kernel filesystem call; ordinary storage reliability remains a separate gate.
