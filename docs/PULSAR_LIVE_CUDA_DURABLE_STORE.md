# Durable live CUDA evidence store

Final live CUDA evidence now has a private transactional SQLite store. Publishing one admitted immutable evidence object atomically creates the table, inserts canonical manifest/summary and original receipt/trace blobs, and raises `user_version` from 20 to 21. Failed publication and outer transaction rollback preserve the preceding schema and rows. Ordinary CPU state does not create this table or acquire the new barrier.

The store requires format-4 ownership metadata, admitted storage and exact current project/source/revision membership. Its sealed object keeps the 512 MiB parsing/retention claim and reserves twice its row bytes plus 1 MiB for publication/WAL overhead; the resource pool also preserves its existing 16 MiB filesystem margin. The caller must retain those claims through commit. Existing format-4 ownership, CUDA intent/evidence and portable readers operate through a checked schema-20 base view of schema 21; no old table layout is reinterpreted. Native capture checks the same base view. This does not grant launch authority.

Startup validates new rows through a read-only connection before opening the worker ledger, then rechecks before writable SQLite/WAL setup. The reader requires the exact table/header combination, bounded scalar types and blobs, no more than 256 rows or 256 MiB, indexed identity correspondence, project/source membership and a project revision at least as new as the historical record. It reserves memory before loading each row's blobs and invokes strict canonical/original-byte verification. Stored guest/model/runtime paths are metadata; readback does not follow them or load CUDA. Missing tables, downgraded/future headers, malformed layouts, tampering and insufficient memory fail closed.

Four store tests cover original-byte publication, preserved ownership/portable-marker writers, historical revisions, storage/memory refusal, rollback/duplicates/current-revision refusal, sixteen tampering cases and actual row/aggregate capacity limits. The Engine startup test accepts healthy schema21 and rejects downgrade, missing table and altered trace with committed database/WAL/ledger bytes unchanged. A separately pinned schema-20 application refuses new state without changing those bytes; the current Engine reopens it.

The native fixture directly retains actual consuming-Finish bytes after Stop and cleanup, checks exact SQLite readback, drops admission, restarts the Engine and validates the retained row again. It uses the existing test-inserted registry and private startup bridge. This is a storage harness, not a production finalizer or public GPU lifecycle. Authored startup fixtures explicitly rebind prior native envelope metadata to Engine-created projects/sources; they establish consistency/refusal only and are separate from fresh native evidence.

The [evidence packet](evidence/roadmap-2026-10-07/live-cuda-durable-store/) retains source archives, raw gates, compiled-reader evidence and original native/SQLite outputs. Final serial gates pass 1,016 workspace tests (55 ignored), 540 CUDA Engine tests (54 ignored), the explicit preceding-reader and native live/offline cases, nine CPU application cases without skips, the default build and 262 structural checks. All 353 final source/archive records and 80 native/model supplier records match. Independent SQLite readback confirms one schema21 row, exact original receipt/trace bytes, canonical manifest identity, three GPU runs/nine CUDA computation events and no foreign-key errors. The prior eight-case private stream campaign is a preceding source subject and was not rerun for this store-only change. The initial startup fixture failed a foreign-key check because directly copied project rows lacked required revision/history records. Its failure log remains; the correction uses Engine-created project/source state and does not weaken production validation.

Public GPU routing, Engine-owned graceful finalization/closing state and lease/grant/revision rechecks at publication, final capture-report linkage, automatic scheduling, continuation and exhaustive recovery remain unfinished. Consistent database blobs are not proof of an authorized current capture. Known parallel-test failures and all model/media, six-axis performance, physical Handy, platform, human and release gates remain open.
