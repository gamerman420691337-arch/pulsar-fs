# Explicit migration of stopped local library batches

Migration creates a successor batch under a new explicit recipe. It preserves the original record instead of rewriting accepted work. Only entries not ReadyForPublication enter the successor; captured source bytes, destinations and existing imported projects are reused. Changing an external media file cannot replace the captured input. Audio/visual publication axes must remain the same.

Read the original status, save that exact response, author a replacement recipe JSON and choose a fresh migration request ID:

```sh
pulsar library-batch-status ORIGINAL > observed.json
pulsar library-batch-migrate ORIGINAL --observed-report observed.json --recipe replacement.json --request-id SUCCESSOR
pulsar library-batch-run SUCCESSOR --publication-state NEW_PRIVATE_JOURNAL
```

The CLI accepts a plain LibraryBatchReport or its library_batch response wrapper. It parses the observed report and hashes its canonical typed serialization. A stale observation, changed project revision, missing current project grants, changed captured bytes or existing destination refuses. A selected-pack recipe carries the exact currently approved manifest digest and selection revision; ordinary fresh pack/profile/runtime admission repeats before publication of the successor. A migration never imports, selects or approves a pack.

In the desktop Library batches panel, read original status, provide the replacement recipe JSON and migration request ID, then choose Create successor from inspected batch. The background intake retains the parsed recipe and observed digest before mutation. File edits cannot rewrite a retained retry. Inspect the successor, choose a fresh publication journal and run explicitly. The old journal cannot be rebound to the new batch. Existing original ReadyForPublication entries can finish their ordinary publication; the original scheduler stops before further generation and never follows the successor automatically.

An original pending mutation or missing positive generation acknowledgement refuses. For a recorded accepted job, migration reconstructs the original request with its current authenticated context and requires the exact positive cached job receipt, matching project/revision/job, current failed or cancelled state, no candidate and absent Worker ownership. Only the successor clears that job binding and old generation effect; the original keeps them. Queued, running, paused, interrupted and completed-but-uncommitted work must first use its original recovery path. Batch cancellation remains final and cannot be migrated. Ordinary terminal state and Worker ownership checks are software evidence, not physical-device retirement proof. The native failure/replacement campaign covers failed jobs; the cancelled-job branch has no separate native migration receipt.

Original stop, successor record, exact source/model/document memberships, lineage and replay acknowledgement share one transaction. Reader floor 32 adds an exact-layout lineage table, permits at most 16 continuation links and retains existing batch capacity limits. Pack and cancellation operations cannot downgrade the barrier. Release descendants before ancestors; release preserves project/job history, snapshots retained by other owners and published output files. An original with a successor cannot advance, cancel or acquire another successor.
